# 多租户与节点部署设计

本文说明租户资源模型、隔离机制、组件职责与调度方式，以及 Worker 如何水平扩缩容。

对应主文档 `技术设计方案.md` 第 4 章，本文是其详细展开。表结构见 `数据模型设计.md`，不在此重复字段。

## 1. 设计目标

多个租户共享同一套 Gateway、Worker 与存储服务。平台需要回答四个问题：

1. 一个租户拥有哪些资源，这些资源如何关联；
2. 不同租户的配置、数据、工具、日志与密钥如何互不干扰；
3. 一条消息如何被路由到正确的租户、正确的 Agent 版本、正确的会话；
4. Worker 增减实例时，会话如何不中断、顺序如何不乱。

## 2. 租户资源模型

### 2.1 整体关系

```text
Tenant
└── Agent App
    ├── Agent Version        配置是什么
    ├── Agent Deployment     当前发布哪个版本
    ├── Channel Binding      哪个 IM 账号进来
    ├── Backend Binding      数据存到哪里
    └── Audit Policy         记录什么、脱敏什么
```

`Tenant` 是资源归属与隔离边界。Agent 的配置与运行数据归属于具体的 Agent App。

### 2.2 三层 Agent 模型

平台对 Agent 采用 App / Version / Deployment 三层模型，职责严格区分：

| 层 | 回答的问题 | 可变性 |
|---|---|---|
| Agent App | 这是哪个 Agent，如客服、运维、数据分析 | 基本信息可改 |
| Agent Version | 这一版的配置是什么 | **发布后不可变** |
| Agent Deployment | 某个环境当前用哪个版本、各占多少权重 | 随时可改，即灰度与回滚 |

版本不可变是整个平台的基础约束。Prompt、模型、Tool、扩展、MCP、Skill 任一项变化都创建新版本，不原地修改。由此获得三个性质：

- 配置变更可追溯，回滚只需改 Deployment 权重；
- Runtime 可按版本缓存且缓存永不失效；
- 版本回滚时能力配置随之回滚，不会出现「版本没变但权限已变」。

### 2.3 版本承载的配置

一个 Agent Version 包含：

```text
Prompt 与模型配置       直接作为 agent_versions 的列
Tool 绑定              agent_tool_bindings      allow / deny / ask
扩展绑定               agent_extension_bindings plugin / guardrail / callback
MCP 绑定               agent_mcp_bindings
Skill 绑定             agent_skill_bindings
知识库绑定             agent_knowledge_bindings
```

Prompt 与模型是「一个版本恰好一份」的定长配置，作为列存放；四类能力配置是不定长列表且会持续增长，拆为独立绑定表。拆表理由与代价见 `数据模型设计.md`。

### 2.4 Deployment 与灰度

一行 Deployment 代表一个环境，各版本权重存于 `routes` JSON：

```json
[{"version": "v1", "weight": 90}, {"version": "v2", "weight": 10}]
```

一行一环境而非一行一版本，因此调权重与回滚都是单行更新，天然原子，不会出现权重之和不为 100 的中间态。

Gateway 在**创建会话时**按权重选定版本并写入 `sessions.agent_version`，此后该会话固定使用该版本。因此调整权重或回滚都不影响进行中的会话。

### 2.5 Channel Binding

外部 IM 账号与租户、Agent 的绑定：

```text
企业微信应用 → 租户 A → 客服 Agent → prod Deployment → 按权重选定版本
```

Channel Binding 默认关联 Deployment，由 Deployment 决定版本；同时保留固定版本能力，用于测试通道或内部调试固定使用某一版本。

### 2.6 密钥引用

配置库中只保存引用，不保存明文：

```text
secret://prod/tenant-a/model/primary-api-key
```

引用分散在使用它的表上（`channel_bindings.secret_ref`、`agent_versions.model_api_key_ref`、`backend_configs.dsn_ref`），不单独建密钥表。明文保存在 Secret Manager，Worker 装配 Runtime 时按租户与用途读取，只在内存中使用。

## 3. 租户隔离

隔离不是给每张表加一个 `tenant_id` 字段，而是五个维度同时成立。

| 维度 | 隔离方式 |
|---|---|
| 配置隔离 | 读取配置的查询一律以 `tenant_id` 起头，Worker 只能加载当前租户目标 Agent 的配置 |
| 数据隔离 | Session、Event、Summary、Memory、Knowledge、Artifact、Audit 均携带 `tenant_id`；Storage Router 按租户绑定选后端 |
| 工具权限隔离 | Tool 调用前检查租户、Agent 版本、IM 用户、运行环境四者；Tool 内部访问业务数据时同样按租户过滤 |
| 日志隔离与脱敏 | 日志与审计携带 `tenant_id`，密钥、Token、个人信息统一经 Redactor 脱敏 |
| 密钥隔离 | 不同租户的 Secret Reference 与访问权限分开管理，不可跨租户读取 |

隔离的起点是 Gateway：它从可信的通道绑定关系确定 `tenant_id`，构造租户上下文，此后该上下文贯穿全链路。

**Runtime 缓存键必须包含 `tenant_id`。** 不同租户可能使用相同的 Agent 名称与版本号，缓存键缺少租户维度会导致模型、Tool、知识库与密钥跨租户混用，这是隔离中最容易被忽略的一处。

## 4. 组件与职责

| 组件 | 职责 | 所在进程 |
|---|---|---|
| Channel Adapter | 接收 IM 回调、验签解密、身份映射、转统一消息；出站回复 | 入站在 Gateway，出站在 Worker |
| Agent Gateway | 入站幂等、租户与 Agent 识别、会话定位、版本选择、写信箱并投递队列 | Gateway |
| Session Scheduler | Session 租约与信箱，保证同一会话顺序执行 | 共享库，两侧都用 |
| Agent Worker | 装配 Runtime，执行 Runner、模型、Tool 与存储读写 | Worker |
| Runtime Registry | Worker 本地 Runtime 缓存，可丢失、可重建 | Worker |
| Storage Router | 按 `tenant + agent + data_type` 选择后端 | 共享库 |
| Admin API | 租户与 Agent 配置的增删改查 | Gateway |
| Telemetry | Metrics、Trace、审计埋点 | 两侧 |

Session Scheduler **不是独立部署的服务**，而是 Gateway 与 Worker 共用的调度库，状态全部保存在 Redis。

## 5. 调度模型

### 5.1 Gateway 与 Worker 不互相调用

Gateway 与 Worker 是两个进程，协作只通过两条通路：

```text
消息队列：Gateway 投递待处理提示，Worker 消费
共享存储：Redis 与 MySQL，两侧各自读写
```

**Gateway 不维护 Worker 列表，不做健康检查，也不选择由哪个 Worker 执行。** 队列承担异步与扇出，由消费者自行争抢。这样 Worker 的增减对 Gateway 完全透明，不需要服务发现与负载均衡。

### 5.2 顺序由租约与信箱保证

同一会话的顺序不依赖队列的顺序特性，而由 Redis 上的两个结构保证：

```text
Session 租约：同一时刻只有一个 Worker 能处理某个 Session，带 TTL 自动过期
Session 信箱：该 Session 待处理的消息，按到达顺序排列
```

执行过程：

```text
Gateway 写入信箱 → 通过队列投递提示
→ Worker 抢占租约，抢不到则直接放弃本次提示
→ 持有租约期间排空信箱，并持续续期
→ 信箱为空后释放租约
```

租约**按轮持有**，范围是一次排空信箱的时间，不是整个会话生命周期。因此同一会话的下一轮消息可由任意健康 Worker 处理。

这一设计使队列的契约被压到最薄：

```text
at-least-once 分发
不要求有序
不要求可靠
```

顺序性由租约与信箱保证，消息不丢由「幂等记录先落库再 ACK」保证。契约越弱，可替换性越强。

### 5.3 消息路由过程

```text
IM 回调到达 Gateway
→ 按 webhook_path 反查 channel_bindings，得到 tenant_id 与 agent_app_id
→ 按 channel_binding_id + scope + scope_key 定位或创建 session
→ 新建会话时按 Deployment 权重选定 agent_version 并固化
→ 幂等记录落库 → 回 ACK → 写信箱 → 投递队列
```

入站三步顺序固定为**幂等记录落库 → ACK → 入队**。先落库保证即使入队失败也有可靠记录可重放；先 ACK 保证 IM 平台不因超时重投。

## 6. Runtime 装配与缓存

### 6.1 装配由配置驱动

Worker 收到提示后，按 Runtime Key 查本地 Registry：

```text
Runtime Key = tenant_id + agent_app_id + agent_version
```

未命中则从配置库读取并装配：

```text
读 agent_versions            得到 Prompt 与模型配置
读 agent_tool_bindings       得到 Tool 列表与 allow / deny / ask
读 agent_extension_bindings  按 kind 分组，依 priority 排序
读 agent_mcp_bindings
读 agent_skill_bindings
→ 构建 Model、Tool、Plugin / Guardrail / Callback
→ 构建 Agent 与 Runner
→ 写入 Registry
```

五次读取的键完全一致，可合并为一次查询后在内存分组。

**装配返回 Agent 接口而非具体类型**，扩展按列表遍历挂载而非写死。这样后续增加 Graph 编排只是装配内部多一个分支，增加 Guardrail 只是往列表追加。

相同 Runtime Key 的并发装配需要加锁，避免多个请求重复构建同一个 Runtime。

### 6.2 缓存管理

配置库是权威来源，Registry 只是可丢失、可重建的本地缓存。已发布版本不可变，因此缓存不会失效，只需处理容量与生命周期：

- 长时间未使用的 Runtime 按 `idle_ttl` 淘汰；
- 版本下线后停止接收新请求，正在执行的请求完成后再释放；
- 配置版本变化时加载新 Runtime，不原地修改旧版本；
- Worker 关闭时调用 Runner 及相关资源的 `Close()`。

## 7. 水平扩缩容

### 7.1 无状态 Worker，不需要 sticky session

**结论：不需要 sticky session。**

理由是 Worker 本地只缓存 Runtime，不保存任何唯一业务状态：

```text
Agent 配置与版本  → 配置库（权威）
Agent Runtime    → Worker 本地缓存（可重建）
Session / Memory → 共享存储（Redis + MySQL）
```

会话绑定的是 Agent 版本，不是 Worker 实例：

```text
session_id → tenant-a / customer-service / v2
第一次请求 → Worker 1
第二次请求 → Worker 3        ← 完全允许
```

新 Worker 装配相同版本的 Runtime 后，从共享存储读取上下文即可继续处理已有会话。并发安全由 Session 租约保证，而非由「同一会话总是落到同一 Worker」保证。

### 7.2 Runtime 加载策略

同一个 Agent Runtime 可以同时加载到多个 Worker，以提高并发与可用性，但不应无控制地加载到全部 Worker。

| 方式 | 适用 |
|---|---|
| 启动预加载 | 平台默认 Agent、高频 Agent、重要租户核心 Agent |
| 请求懒加载 | 调用频率较低的 Agent，避免所有 Worker 都提前占用资源 |
| 专属 Worker 池 | 需独立沙箱、大量 MCP 连接、或隔离要求高的 Agent |

可为 Deployment 配置运行策略，第一版不必全部实现，但数据模型与接口保留扩展位：

```yaml
runtime_policy:
  load_mode: lazy          # lazy / preload / dedicated
  preferred_replicas: 2
  max_replicas: 4
  idle_ttl: 30m
```

在队列模型下没有「Gateway 优先把请求发给已加载该 Runtime 的 Worker」这一说，因为 Gateway 不选 Worker。若后续需要 Runtime 亲和以减少重复装配，做法是**按 Runtime Key 分组消费**（一组 Worker 只订阅部分租户或 Agent），而不是让 Gateway 感知 Worker 状态。这属于优化，不改变上述结构。

### 7.3 扩容

```text
新增 Worker → 加入消费组 → 按策略预加载部分热门 Agent
→ 开始争抢队列消息 → 其余 Agent 在提示到达时懒加载
```

新 Worker 不需要复制任何 Agent 配置、Session 或 Memory。

### 7.4 缩容与故障

缩容按序处理：

1. 停止消费新消息；
2. 等待正在执行的请求完成；
3. 超时后取消未完成请求（通过 `context` 取消）；
4. 关闭 Runner、连接与后台任务，排空 Event 通道；
5. 退出进程。

Worker 故障时无需任何通知机制：它持有的 Session 租约会在 TTL 到期后自动释放，其他 Worker 抢到租约后从共享存储恢复上下文继续处理。**租约 TTL 就是故障恢复时间。**

若故障发生在执行过程中，是否重试由 `inbound_events` 的状态机判断，避免重复执行 Agent 与 Tool。详见 `故障恢复与运维设计.md`。

### 7.5 Worker 状态上报

Worker 可定期上报健康状态、当前执行请求数、并发会话数、CPU 与内存、已加载 Runtime Key 及其最近使用时间。

在队列模型下这些数据**用于运维观测与容量评估，不用于调度决策**——调度由争抢完成，不需要中心化的状态视图。

## 8. 设计原则汇总

1. Tenant 是资源归属与隔离边界，隔离在配置、数据、工具、日志、密钥五个维度同时成立；
2. Agent 采用 App / Version / Deployment 三层模型，Version 不可变，Deployment 承载灰度与回滚；
3. 会话创建时固化版本，此后不随发布变化；
4. Gateway 与 Worker 不互相调用，只通过队列与共享存储协作；
5. Gateway 不做服务发现与 Worker 选择，由消费者争抢；
6. 同一会话的顺序由 Session 租约与信箱保证，不依赖队列的顺序特性；
7. Worker 无状态，不需要 sticky session；
8. Runtime 由配置驱动装配，按 `tenant + agent + version` 缓存，缓存键必须含 `tenant_id`；
9. 配置库是权威来源，本地 Registry 只是可重建的缓存；
10. 密钥只存引用，运行时按租户读取。
