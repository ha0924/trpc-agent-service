## 状态标注的核实方法

每条状态都要能指到具体证据，指不到的降级。本文的标注按以下强度排序，标注时取**最弱**的那一级：

| 强度 | 依据 | 例 |
|---|---|---|
| 最强 | 外部系统实测 | E2 企业微信长连接：真实端点收发双向 |
| 强 | 本机端到端实测 + 单元测试 | B9/B10 租约与信箱：双 Worker 序号 1..10 连续 |
| 中 | 有调用点且有单元测试 | G 全部 15 个 Recorder 方法均有调用点 |
| 弱 | 有代码但无调用点 | **不计 ✅**。F5 的 `tool_approvals` 即此类 |
| 最弱 | 仅有表、常量或接口 | 📄 或 ❌。四个 `DataType` 常量即此类 |

「有代码但无调用点」不计完成，是因为本项目已三次栽在这上面：`Run()` 死代码、`max_message_attempts` 形同虚设、三类指标定义了从不调用（台账 §八 #4 #7 #9）。**函数存在不等于行为成立。**

## 一、需求理解

题目要求把 Agent 从「单点 demo」变成「平台化服务」。拆开看，平台化意味着四件事，缺一件就退回 demo：

1. **多租户** —— 多个部门/业务线共用一套服务，配置、数据、工具权限、审计互不可见；
2. **节点化** —— Worker 可水平扩展，单点故障不丢消息，不依赖 sticky session；
3. **多后端** —— 不同租户可选不同存储，且后端可替换、可迁移；
4. **多入口** —— 至少两类 IM 通道触达，加上管理面与 API。

框架（tRPC-Agent-Go）已提供 Agent 编排、Tool/MCP、Session/Memory/Knowledge/Artifact、Plugin/Guardrail、Telemetry、HTTP 服务化、OpenClaw Channel。**平台层要做的不是重新实现这些，而是给每一项加上「租户维度」**：框架的 `session.Service` 是一个实例，平台要按租户路由到不同实例；框架的 Guardrail 是一组回调，平台要按租户从数据库读出该挂哪几个。

这个判断决定了功能清单的形状——大部分功能是「装配」与「路由」，而不是「实现」。详见 [框架复用与扩展.md](框架复用与扩展.md)。

**这块曾是全清单里落差最大的，第一批开发已补齐。** 任务描述第一句是「平台需要支持多个租户**创建和部署**自己的 Agent」，而此前建租户、建 Agent、发版本全部只能手写 SQL——「部署」有了（A5），「创建」不存在。

现在 `scripts/acceptance_control.sh` 可以只用 HTTP 接口走完「建租户 → 建 Agent → 建版本 → 配工具 → 发布 → 绑通道 → 发消息拿回复」，全程一句 SQL 都不用。跑不到底就说明链路里还有依赖手写 SQL 的环节，这比断言「接口齐全」更能证明该条成立。

两处设计取舍值得记下：

- **已发布版本不可改由 SQL 保证，不是靠约定。** `UPDATE ... WHERE status = 'draft'` 使并发下也成立，而 Go 侧的检查会有竞态窗口。这是缓存的 Runtime 永不过期的前提。
- **绑定列表整组替换而非增量。** 列表本身就是权限授予，增量更新会留下一个「Agent 持有谁也没批准过的工具集」的窗口；在已发布版本上，那个窗口就是权限提升。

剩下 A7/A9 未做：两者都依赖尚未落地的存储能力（知识库、多后端配置表），先做配置面是空转。

README 两处措辞：

> §44「支持企业微信、微信客服、微信公众号、Telegram 或其他 IM 通道中的**至少两类**」

[完成度台账.md](完成度台账.md) §五③ 记为 ✅，依据是 Mock + 企业微信回调 + 企业微信长连接三个实现。本文认为按字面严格读应记 ⚠️，两条理由：

1. `mock` 是平台自己写的测试通道，用它凑「两类」等于自证；
2. 回调与长连接的差异确实巨大（方向相反、有无公网、有无加解密、回复路径不同），但它们是**同一平台的两种接入方式**。README §44 枚举的是**平台**（企业微信、微信客服、微信公众号、Telegram），不是接入方式。

需要二选一：补一个真实通道（E3–E6 任一），或在台账中明示「两类」按接入方向计并给出理由。**裁决前此条以本文的 ⚠️ 为准**——这是 §「与《完成度台账》的分工」中声明的唯一例外。

**但协议须自研**：`openclaw/plugins/telegram` 只是 204 行注册薄壳，实现在 `internal/` 下不可引用（见 [框架复用与扩展.md](框架复用与扩展.md) §2.5 更正）。此前本文与设计文档都写「有现成实现可适配」，是误判。

**长连接的真实环境验证状态**：收发双向已通（见 [IM通道接入设计.md](IM通道接入设计.md) §9.2.1）。四项文档只用文字描述的字段形态已实测定形；联调过程查出并修复两个静默丢回复的缺陷（台账 §八 #10 #11）。

分布的形状比比例更说明问题：

- **链路与支撑几乎满格** —— B（11/13）、G（12/12）、H（7/7）、I（9/11）、L（8/8）。消息从入站到回复这条路径上的并发、幂等、故障、可观测、隔离都经过实测。
- **平台的「面」是窄的** —— A（管理面只读）、C（只有 LLMAgent）、D（只有 Session 一类数据）、E（只有一类真实 IM）、K（无 API 服务化）。

一句话：**深度够，广度不足**。框架给的 Memory/Knowledge/Artifact/MCP/编排/服务化，接口位都留好了，里面是空的。

**关于「深度够」这个结论的证据强度，需要区分对待。** 绝大多数 ✅ 的依据是单元测试加本机端到端脚本——即自证。只有 E 模块的企业微信长连接经过**外部系统验证**：真实端点、真实消息、真实回复，且该过程查出两个静态检查与单元测试都没拦住的缺陷（台账 §八 #9 #10 #11）。

这个对比本身是有信息量的：一条链路在自证下全绿，接真实系统后仍暴露三个缺陷，其中两个会静默丢回复。因此对其余模块「已跑通」的可信度，应按「未经外部验证」打折——它们没有被证伪，但也没有被真实系统检验过。

## 五、优先级

按「投入 ÷ 消掉的质疑强度」排序。前两项是 README 字面要求未满足，第三项是验收标准点名要求，第四项是「功能存在但不成立」。

| 序 | 事项 | 依据 | 工作量参考 |
|---|---|---|---|
| 1 | 补第二类真实 IM（建议 Telegram） | E0 分歧项，「至少两类」 | 协议须自研（framework 的实现在 `internal/`）；`Channel` 接口与两种 `inbound_mode` 已就位 |
| 2 | 写入类 Admin API（建租户/建 Agent/发版本） | A2–A4，任务描述「创建和部署」 | `store` 层读 SQL 与事务模式可同构套用 |
| 3 | Memory 接通一路 | D3 + D8 + D11，验收标准第 2 条 | 框架 `memory/redis` 子模块现成 |
| 4 | F5 危险工具审批 | 状态机未接（非仅缺端点），见 F5 说明 | 需接 `tool_approvals` 写入 + Admin 放行端点，与第 2 项同批 |

**第 4 项为何前置到压测之前。** 它现在的状态是「拦截生效、审计留痕，但状态机未接」，实际效果等价于「高风险工具一律拒绝」。这与 `Run()` 曾是死代码同源：**表、SQL、函数都在，零调用点**。这类缺口比彻底没做更容易误导评审，因为一应俱全，看起来就是做完了。且第 2 项本就要写 Admin 写端点，放行端点顺路完成。

**压测（J1）后移的理由。** 压测的产出是数字，而数字的说服力取决于被压系统的完整度。当前 Memory 未接、仅一类真实 IM、管理面只读，压出的数字只能描述「这个形态的吞吐」，补完功能后仍需重压。另外 README §J1 要求的是**容量评估**，给出评估方法、瓶颈定位与扩容依据也构成交付，不必然等同于实测数字——但 [故障恢复与运维设计.md](故障恢复与运维设计.md) §9 目前连方法都未给出，这才是该条真正的缺口。
