## 一、需求理解

题目要求把 Agent 从「单点 demo」变成「平台化服务」。拆开看，平台化意味着四件事，缺一件就退回 demo：

1. **多租户** —— 多个部门/业务线共用一套服务，配置、数据、工具权限、审计互不可见；
2. **节点化** —— Worker 可水平扩展，单点故障不丢消息，不依赖 sticky session；
3. **多后端** —— 不同租户可选不同存储，且后端可替换、可迁移；
4. **多入口** —— 至少两类 IM 通道触达，加上管理面与 API。

框架（tRPC-Agent-Go）已提供 Agent 编排、Tool/MCP、Session/Memory/Knowledge/Artifact、Plugin/Guardrail、Telemetry、HTTP 服务化、OpenClaw Channel。**平台层要做的不是重新实现这些，而是给每一项加上「租户维度」**：框架的 `session.Service` 是一个实例，平台要按租户路由到不同实例；框架的 Guardrail 是一组回调，平台要按租户从数据库读出该挂哪几个。

这个判断决定了功能清单的形状——大部分功能是「装配」与「路由」，而不是「实现」。详见 [框架复用与扩展.md](框架复用与扩展.md)。

**分歧项（本文与台账不一致，需裁决）**

README 要求「企业微信、微信客服、微信公众号、Telegram 或其他 IM 通道中的**至少两类**」。

[完成度台账.md](完成度台账.md) §五③ 将此条记为 ✅，依据是 Mock + 企业微信回调 + 企业微信长连接三个实现。本文认为按字面严格读应记 ⚠️：`mock` 不是真实 IM 通道；回调与长连接是同一平台的两个**接入方向**，不是两个**通道类别**。严格计数下真实 IM 覆盖为 **1 类**。

需要二选一：补一个真实通道（E3–E6 任一），或在台账中明示「两类」按接入方向计并给出理由。**在裁决前，此条以本文的 ⚠️ 为准**——这是 §「与《完成度台账》的分工」中声明的唯一例外。

补 Telegram 成本最低：纯 HTTPS + long polling，无验签无解密，`Channel` 接口已抽好；且其差异维度（无需公网、无加密、原生流式编辑）正好为 [IM通道接入设计.md](IM通道接入设计.md) 的差异对比补一列真实数据。

**长连接的已知缺口**：事件回调不作答（5 秒窗口容不下一次 Agent 执行）、多媒体 `aeskey` 未解密、临时素材分片上传未实现、stream 绑定需重启 Gateway 才生效、群聊代码路径存在但未对真实群验证。
