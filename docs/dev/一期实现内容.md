# 一期实现内容

- 周期：2026/08/28 – 2026/08/31
- 目标：按架构图搭出完整拓扑，跑通端到端链路，内容单薄但结构真实

一期不是简化版拓扑，而是完整拓扑加单薄内容。判断依据是后期难改的进一期，后期只是增加同类实例的往后放。

## 1. 层级取舍

原则：架构图上的**框**可以只做一个，架构图上的**箭头**必须全部打通。

| 架构图分层 | 一期范围 |
|---|---|
| 外部消息源 | 仅 HTTP 一路，IM 与 AG-UI、A2A 不做 |
| 接入与适配 | Channel 仅 Mock；统一消息模型、身份映射、入站幂等均需落地 |
| 网关与调度 | 租户识别、Agent 与版本路由、租约与信箱均需落地；鉴权限流不做 |
| Agent 执行层 | 单副本运行，但需保证多副本并行无冲突 |
| 框架能力 | 仅 LLMAgent 与两个 Tool，Graph、MCP、Guardrail 不做 |
| 共享存储层 | Storage Router 需真实路由，下游仅接 Session 一路 |
| 平台控制面 | 配置表建好并写入一条数据，Worker 从配置库读取；Admin API 不做 |
| 可观测层 | 仅 `trace_id` 贯穿日志，Collector 与 Metrics 不做 |

举例说明该原则：共享存储层在图上有 Session、Memory、Knowledge、Artifact、Audit 五个后端，一期只做 Session 一个，但 `Worker → Storage Router → 后端` 这条链路必须是真实路由。二期增加 Memory 只是注册一个后端，不改结构。

同理，控制面到 Worker 的配置发布这条虚线一期必须打通，因为它决定了 Runtime 是读配置装配还是写死一个 Agent，这两种写法差异很大，后补等同重写。

## 2. 实现内容

- Gateway 与 Worker 拆为两个进程，中间通过消息队列异步分发；同一 Session 的顺序由 Session 租约保证，不依赖队列的顺序消息特性；
- 配置从配置库读取，不硬编码：一期建表 12 张，预置一条可运行链路的数据，详见 `一期建表与初始数据.md`；
- Runtime 按 `tenant_id + agent_version` 动态装配，不写死单个 Agent；
- 租户上下文（`tenant_id`、`agent_app_id`、`session_id`、`request_id`、`trace_id` 等）全链路贯穿；
- Storage 按 `tenant_id + agent_app_id + data_type` 真实路由，映射先从配置文件读取，只注册一个后端但走完整路由逻辑；
- 入站处理顺序固定为：幂等记录落库 → ACK → 入队；
- 通道只实现 Mock Channel（HTTP 收发），但 `Channel` 接口与能力描述符按真实通道的形状定义。

## 3. 核心接口

四个接口在本期定死，后续两期只填实现、不改结构。

| 接口 | 职责 | 一期实现 |
|---|---|---|
| `Channel` | 消息收发与通道能力描述 | Mock 通道，HTTP 收发 |
| `SessionDispatcher` | 投递与消费待处理提示 | Redis List |
| `StorageRouter` | 按 `tenant + agent + data_type` 选择后端 | 仅注册 Session 一路，走 Redis |
| `RuntimeProvider` | 按 `tenant + version` 装配 Runtime | LLMAgent 加两个 Tool |

`types` 包先落地。统一消息模型、租户上下文与这四个接口确定后，其余包即可并行开发，互不阻塞。

## 4. 结构性约束

Graph、MCP、Guardrail、Metrics 均不在一期实现，但它们的挂载结构必须在一期留好。区分标准是后补成本：埋点内容（增加计数器、补审计字段）随时可加；埋点的挂载结构（context 如何传递、callback 挂在何处）一旦缺失，后补需要改动所有签名。

- **`context.Context` 一路到底**。`tenant_id`、`trace_id`、`request_id` 通过 context 从 Gateway 传递到模型、Tool 与存储调用。任何一处方法签名缺少 context，后续加埋点即需改动全部实现，这是一期唯一真正无法后补的部分；
- **Runtime 装配走 spec，不写死**。装配时接收待挂载的 callback 与 guardrail 列表，一期该列表只放一个日志实现。二期增加 Guardrail 是往列表中追加，不改装配签名；
- **不绕过框架挂载位**。tRPC-Agent-Go 已提供 Plugin / Guardrail / Callback 的挂载位，一期不自建 hook，也不直接调用模型绕过这些位置；
- **装配返回 Agent 接口，不返回具体类型**。返回接口后，二期增加 Graph 编排只是装配内部多一个分支；返回具体类型则调用方全部需要改动；
- **Worker 逐个消费 Event**。消费 Runner 的 Event 通道时逐个交给输出函数处理，不攒完整个回复再返回。一期该输出函数只做缓冲后一次性发送。

另有一处顺序约束需在一期留出调用位置：危险 Tool 的审计记录必须写在副作用发生之前。一期没有危险 Tool，但该调用点的位置需预留，避免后续将审计写成事后记录。

## 5. 不可省略项

两处一期不可省略，二者决定整体代码组织，后期补齐等同重写：

- Gateway 与 Worker 必须是两个进程，且中间隔着队列；
- Runtime 必须由配置驱动装配。

## 6. 出口标准

两个进程 + 消息队列 + Redis + MySQL 起来后：

```text
发一条消息 → 立即返回 ACK
→ Worker 消费并执行 Agent
→ Mock 通道收到回复
→ Redis 中存在 Session 与 State
→ MySQL 中 Session Event 顺序正确
→ 日志中 trace_id 从 Gateway 贯穿至 Worker
```
