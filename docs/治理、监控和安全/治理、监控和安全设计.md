# 治理、监控和安全设计

## 1. 设计目标

平台同时服务多个租户、多个 Agent 和多个 IM 通道。除了让 Agent 能正常回答问题，还需要保证：

- 不同租户使用各自的工具、模型和密钥；
- Agent 不能调用未授权或高风险的工具；
- 平台能够知道一次请求经过了哪些步骤、哪里慢、哪里失败；
- 能够按租户统计 Token 和成本；
- 可以追踪谁在什么时间通过哪个 IM 使用了哪个 Agent 或 Tool；
- IM Token、模型 API Key、数据库密码等敏感信息不会出现在日志、Trace 或错误报告中。

本设计复用 tRPC-Agent-Go 的 Plugin、Guardrail 和 Callback 等扩展能力，在 Agent 执行链路中加入治理、监控、审计和脱敏。

## 2. 总体思路

治理、监控和安全能力不是单独的一条业务链路，而是附着在正常 Agent 执行过程中：

```text
IM 平台
→ Channel Adapter
→ Agent Gateway
→ Session Scheduler
→ Agent Worker / Runner
→ LLM / Tool / MCP
→ Session / Memory / Audit Storage
→ IM 回复
```

平台在消息进入、模型调用、工具调用、状态写入和 IM 回复等关键位置执行以下能力：

- **Plugin**：提供可插拔的运行扩展，例如上下文注入、回复格式化、成本统计；
- **Guardrail**：执行安全和权限判断，例如工具白名单、预算限制、内容脱敏和二次确认；
- **Callback**：监听生命周期事件，用于指标、Trace、审计和错误记录；
- **Policy**：保存租户和 Agent 的规则，例如允许哪些 Tool、每日预算是多少。

```text
Tenant / Agent Version Policy
→ Worker 构建 Runtime
→ 装配 Plugin / Guardrail / Callback
→ 在 Agent 执行的固定 Hook 中执行治理与观测逻辑
```

## 3. 租户级治理

### 3.1 策略范围

治理策略可以按以下层级配置：

```text
平台默认策略
→ Tenant 策略
→ Agent App 策略
→ Agent Version 策略
→ Channel 或环境覆盖策略
```

规则越具体，优先级越高；但安全规则遵循“只能收紧、不能绕过”的原则。例如平台全局禁止的危险 Tool，租户不能重新开启。

### 3.2 Runtime 装配

Worker 收到请求后，使用以下信息找到或创建 Runtime：

```text
tenant_id + agent_app_id + agent_version
```

Runtime 构建时读取当前 Agent Version 的配置，并装配平台提供的扩展模块。例如：

```text
客服 Agent
├── 租户上下文注入
├── Tool 白名单
├── 敏感信息脱敏
├── 成本统计
└── 审计记录

运维 Agent
├── 租户上下文注入
├── Tool 白名单
├── 生产环境二次确认
├── 预算限制
└── 审计记录
```

租户通过配置选择启用哪些平台扩展及其参数，不直接执行任意自定义代码。

### 3.3 Agent 执行中的 Hook

在一次 Agent 执行中，可以抽象为：

```text
读取 Session / Memory
→ 模型调用
→ 如需要则调用 Tool
→ 再次模型调用
→ 得到最终回复
→ 写回 Session / Memory
→ IM 回复
```

Plugin、Guardrail 和 Callback 在固定位置工作：

| 阶段 | 主要处理内容 |
| --- | --- |
| IM 入站后 | IM 回调验签、用户身份映射、是否允许使用当前 Agent |
| 模型调用前 | 租户上下文注入、模型白名单、预算检查、输入脱敏 |
| 模型调用后 | Token 和成本统计、输出内容检查 |
| Tool 调用前 | Tool 白名单、用户角色、环境限制、参数校验、二次确认 |
| Tool 调用后 | Tool 耗时记录、结果脱敏、错误分类 |
| IM 回复前 | 输出脱敏、消息长度和通道格式处理 |

## 4. 主要治理策略

### 4.1 Tool 白名单和危险操作确认

每个 Agent Version 可以配置允许、拒绝或需要确认的 Tool：

```text
allow：允许调用
deny：禁止调用
ask：需要用户或管理员二次确认
```

例如：

```text
客服 Agent
├── query_order：allow
├── create_ticket：allow
├── refund_order：ask
└── delete_customer：deny
```

Tool 调用前，Guardrail 需要同时检查：

- 当前 Tenant 是否允许该 Tool；
- 当前 Agent Version 是否绑定该 Tool；
- 当前 IM 用户是否有相应角色；
- 当前环境是否允许，例如生产环境；
- Tool 参数是否符合规则；
- 是否需要审批或二次确认。

高风险 Tool 在实际执行前，应先记录允许或确认决策，便于后续审计。

### 4.2 IM 用户权限校验

平台先验证 IM 平台回调是否合法，再将外部用户映射为内部用户：

```text
channel_binding_id + external_user_id
→ internal_user_id
→ role / department / permission_set
```

之后按内部身份判断用户是否可以：

- 使用某个 Tenant 下的 Agent；
- 在群聊中触发 Agent；
- 调用某类 Tool；
- 访问生产环境能力。

例如，外部客户只能使用客服 Agent；内部运维 Agent 仅允许指定员工和管理员使用。

### 4.3 内容安全和脱敏

敏感信息可以在以下阶段处理：

- IM 入站：对明显的敏感内容或非法请求做基础检查；
- 模型调用前：清理不应发送给模型的字段；
- Tool 调用后：清理 Tool 结果中的手机号、身份证号、密钥等字段；
- IM 出站前：对最终回复进行脱敏和内容检查。

敏感内容可以被拒绝、替换为掩码，或在审计记录中只保留摘要。

### 4.4 预算和限额

平台需要支持以下限制：

- 单次请求最大 Token；
- 单次请求最大成本；
- 租户每日或每月成本上限；
- Agent 或 Tool 的调用频率限制。

稳定规则在 Runtime 构建时加载。实时预算余额可以在模型调用前通过缓存、Redis 或预算服务检查。达到上限时，可以拒绝请求、切换低成本模型或返回预算已用尽的提示。

## 5. 监控指标与埋点

### 5.1 基本原则

先在设计中定义需要观测的指标，再在代码实现时于统一边界埋点。埋点主要放在：

```text
Channel Adapter
Agent Gateway
Session Scheduler
Agent Worker / Runner
LLM Client
Tool / MCP Client
Storage Adapter
```

避免在每个 Agent 业务逻辑中重复埋点。

### 5.2 核心指标

| 类别 | 关注指标 | 主要埋点位置 |
| --- | --- | --- |
| 请求 | 请求量、请求总耗时、错误率 | Channel Adapter、Gateway |
| 会话调度 | 排队长度、等待耗时、正在执行数 | Session Scheduler |
| 模型 | 调用次数、调用耗时、输入/输出 Token、模型错误 | 模型调用前后 |
| Tool | 调用次数、调用耗时、失败率、拒绝数 | Tool 调用前后 |
| IM | 入站事件数、重复事件数、投递成功率、投递耗时 | Channel Adapter |
| 存储 | Session / Memory / Knowledge 后端延迟和错误率 | Storage Adapter |
| 治理 | Guardrail allow / deny / ask 数量、脱敏次数 | Guardrail 决策处 |
| 成本 | Token 使用量、模型成本、预算使用率 | 模型调用结束后 |

建议的指标示例：

```text
agent_requests_total
agent_request_duration_seconds
session_scheduler_wait_duration_seconds
llm_request_duration_seconds
llm_input_tokens_total
llm_output_tokens_total
tool_call_duration_seconds
tool_call_errors_total
im_outbound_deliveries_total
im_duplicate_events_total
storage_operation_duration_seconds
guardrail_decisions_total
tenant_cost_total
```

### 5.3 指标标签

指标可以携带受控维度，例如：

```text
channel
agent_app_id
agent_version
model_name
tool_name
storage_type
status
error_type
```

不应把 `session_id`、`request_id`、完整 `user_id` 等高基数字段作为高频 Metrics 标签。这类信息应写入 Trace 或审计记录。

### 5.4 看板与告警

后续可按以下维度建设看板：

```text
平台总览：请求量、成功率、P95 延迟、错误率
模型与 Tool：模型耗时、Token、Tool 耗时和失败率
IM 与存储：IM 投递成功率、重复事件比例、Session 后端延迟
租户成本与治理：成本、预算使用率、拒绝和二次确认次数
```

指标可用于告警，例如 IM 投递失败率升高、模型超时增加、Session 后端延迟过高、租户预算即将耗尽。

## 6. OpenTelemetry 与 Trace

平台采用 OpenTelemetry 作为统一的 Trace 和 Metrics 埋点标准。

一次 IM 消息进入平台时，由 Channel Adapter 或 Gateway 创建 Trace，并通过 `context.Context` 向下传递。`trace_id` 和 `request_id` 贯穿整个链路。

建议的 Trace 结构如下：

```text
im.callback
└── gateway.handle_message
    ├── idempotency.claim
    ├── tenant_agent.resolve
    ├── session_scheduler.dispatch
    └── worker.execute
        ├── runtime.load
        ├── session.load
        ├── memory.load
        ├── llm.generate
        ├── tool.call
        ├── session.persist
        ├── memory.persist
        └── im.outbound_delivery
```

Trace 用于定位某一次请求在哪里慢、为什么失败。Metrics 用于看整体趋势和告警。两者配合使用。

Trace 属性只记录安全、稳定的字段，例如：

```text
tenant.id
agent.app_id
agent.version
channel.type
request.id
tool.name
model.name
storage.type
status
error.type
```

不记录密钥、完整 Prompt、完整 Tool 参数、原始 IM Payload 等敏感内容。

## 7. 审计日志和成本记录

### 7.1 审计事件

审计日志用于回答：

```text
谁在什么时间、通过哪个通道、
使用了哪个 Agent、调用了什么 Tool、
系统为什么允许、拒绝或要求确认、
最后是否成功。
```

建议记录以下事件：

```text
inbound_message
guardrail_decision
model_call
tool_call
session_write
memory_write
outbound_delivery
error
```

### 7.2 最小字段

审计记录至少包含：

```text
tenant_id
channel
user_id
session_id
agent_name
tool_name
decision
latency
error_type
cost
trace_id
```

可扩展字段包括：

```text
audit_id
occurred_at
agent_app_id
agent_version
channel_binding_id
request_id
event_type
model_name
input_tokens
output_tokens
payload_reference
content_redacted
```

不同事件不需要填满所有字段。例如 Tool 调用重点记录 `tool_name` 和 `decision`，模型调用重点记录 Token、成本和模型名称。

### 7.3 写入方式

审计事件由 Callback 或统一 Audit Recorder 生成：

```text
执行链路事件
→ Audit Event
→ Audit Recorder
→ audit_logs
```

普通审计记录可以异步写入，避免影响 Agent 回复速度。涉及危险 Tool、人工确认、生产环境操作等高风险事件，应在实际执行副作用前可靠记录审计决策。

Token 和成本还应写入 Usage 明细，用于按 Tenant、Agent、模型和日期汇总成本。精确成本不能只依赖 Metrics。

## 8. 密钥管理和脱敏

### 8.1 Secret Reference

IM Token、模型 API Key、数据库密码和 Tool / MCP 凭据不保存在业务配置表中。

平台配置只保存密钥引用：

```text
secret://prod/tenant-a/model/primary-api-key
secret://prod/tenant-a/channel/im-token
secret://prod/platform/session-postgres-password
```

真正的明文密钥保存在 Secret Manager、云密钥服务、Kubernetes Secret 或企业内部密钥服务中。生产环境推荐使用具备访问控制、版本、轮换和审计能力的 Secret Manager。

### 8.2 按需使用密钥

Worker 构建 Runtime 时：

```text
读取配置中的 secret_ref
→ 使用工作负载身份请求 Secret Provider
→ 校验 Tenant、用途和环境权限
→ 短时间获得明文
→ 初始化 LLM、IM、数据库或 Tool Client
```

密钥存储时以密文保存；使用时由 Secret Manager 或 KMS 按权限解密，并通过 TLS 返回给 Worker。Worker 使用明文初始化 Client 后，不应继续在普通对象中传播原始密钥。

Worker 解析密钥时必须携带当前 `tenant_id` 和用途，确保 Tenant A 的 Runtime 不会使用 Tenant B 的密钥。

### 8.3 日志、Trace 和错误脱敏

平台提供统一 Redactor，所有输出出口都要经过脱敏：

```text
Logger
OpenTelemetry
Audit Recorder
Error Reporter
HTTP / Tool Client Debug Log
```

默认不允许输出：

```text
Authorization
Bearer Token
API Key
Password
Cookie
IM Token / Secret
数据库 DSN 中的密码
MCP Token
完整 Prompt
完整 Tool 参数和返回
原始 IM Payload
```

常见处理方式：

```text
密钥：替换为 [REDACTED]
手机号、邮箱等个人信息：部分掩码
消息正文：按审计策略脱敏、截断或只记录哈希
Tool 参数：仅记录字段白名单，敏感字段替换为 [REDACTED]
错误：记录 error_type，不直接上报原始错误全文
```

OpenTelemetry Collector 或等价组件可以在导出前再次清洗属性，作为最后一道防线。

## 9. 第一版范围

第一版先完成以下能力：

1. Tenant / Agent Version 级别的 Tool 白名单和 `allow / deny / ask` 决策；
2. IM 用户身份映射和基础权限校验；
3. 模型和 Tool 调用的 Token、耗时、错误和成本采集；
4. IM 投递、Session / Memory 后端的基础指标；
5. 使用 OpenTelemetry 串联完整 Trace；
6. 结构化审计日志和 Tenant 成本 Usage 明细；
7. `Secret Reference + Secret Provider` 抽象；
8. 日志、Trace、错误和审计输出的统一脱敏。

具体监控平台、Trace 后端、Secret Manager 产品和内容审核服务可在实施阶段选择，不影响本设计的接口和边界。
