# 技术栈说明

本文记录平台的技术选型及理由，供实现阶段对照。选型原则是在交付周期内优先可运行与可替换，避免为不需要的能力引入依赖。

## 1. 选型总览

| 位置 | 选型 | 状态 |
|---|---|---|
| Agent 框架 | tRPC-Agent-Go | 已定 |
| Web 框架 | Gin | 已定 |
| 配置与业务库 | MySQL | 已定 |
| 运行时状态 | Redis | 已定 |
| 消息队列 | 未定，一期先用 Redis List 顶替 | 待定 |
| 可观测 | OpenTelemetry | 三期接入 |
| 部署 | Docker Compose | 三期交付 |

## 2. Agent 框架：tRPC-Agent-Go

平台的既定实现框架。可直接复用的能力包括 Agent 编排、`runner.Runner` 执行入口、Tool 与 MCP、Session 与 Memory 的多后端实现、Plugin / Guardrail / Callback 挂载位、以及 Telemetry 埋点。

平台层需要新增的是租户维度的封装：Agent 的注册发布与版本路由、Worker 调度、租户级后端选择、Tool 白名单与密钥注入、租户维度的审计与成本统计。

一期只使用 LLMAgent 与两个 Tool。Graph 编排、MCP、Guardrail 策略在后续阶段接入，但装配结构在一期即按可扩展的形式确定。

## 3. Web 框架：Gin

仅 Gateway 侧使用，承载通道回调入口，二期起承载 Admin API。

Worker 不需要 Web 框架，其入口是队列消费循环，仅需一个健康检查端点。

选择 Gin 而非标准库的理由是二期 Admin API 存在较多 CRUD 与参数绑定，路由与中间件可直接复用。

## 4. 不引入 tRPC-Go RPC 框架

Gateway 与 Worker 之间通过消息队列和共享存储协作，不存在互相调用的 RPC 关系；Admin API 面向管理页面，REST 更直接。因此引入 RPC 框架不产生收益，反而增加 proto 定义与配置成本。

需要区分的是：tRPC-Agent-Go（Agent 框架）与 tRPC-Go（RPC 框架）是两个独立项目，使用前者不要求使用后者。

## 5. 存储：MySQL 与 Redis

MySQL 承担配置与业务数据：租户、Agent App、Agent Version、Agent Deployment、Channel Binding、Backend Binding、Session Event、审计与 Usage 记录。选择 MySQL 而非 PostgreSQL 无特殊技术原因，取其运维熟悉度。

Redis 承担运行时状态：Session State、Session 租约、Session 信箱。这三类数据均需要 TTL 与原子操作，且量级不大——租约与信箱只覆盖"正在执行"的会话，信箱在用户未连发消息时为空。真正体量大的 `session_events` 属于历史数据，落 MySQL。

向量数据库与对象存储在一期不接入，`StorageRouter` 保留其注册位置。

## 6. 消息队列：待定

一期通过 `SessionDispatcher` 接口隔离，实现先用 Redis List 顶替，选型推迟到实现阶段。

可以推迟的原因是队列的职责被刻意压得很薄，契约只有三条：

```text
at-least-once 分发
不要求有序
不要求可靠
```

顺序性由 Session 租约与信箱保证，不依赖队列的分区或顺序消息特性；消息不丢由"幂等记录先落库再 ACK"保证，队列本身可丢。契约越弱，可替换性越强，Redis Stream、Kafka、RocketMQ、Pulsar 均可满足。

队列在架构中承担的是异步与扇出，对应架构图上 Scheduler 到多个 Worker 的分发关系：Gateway 无需维护 Worker 列表或做健康检查，由消费者自行争抢。

若后续替换为正式消息队列，触发条件是治理能力而非吞吐量。本系统受限于 Worker 并发数与模型配额，属并发受限而非吞吐受限，入站 QPS 不构成瓶颈。真正的替换动因是租户级隔离与 QoS、死信与重放的现成工具链、消息保留期与审计回溯、以及跨机房部署。

选型时需注意：Kafka 与 RocketMQ 的顺序消息为队列分区模型，分区数等于并发上限，且扩缩容触发的 rebalance 会中断正在执行的长任务。按上述契约，本系统无需队列提供顺序，因此使用普通 topic 即可，不应启用顺序特性。

## 7. 可观测：OpenTelemetry

三期接入 Trace 与 Metrics，要求 trace 串起通道回调、Gateway、调度、Runner、模型、Tool、存储读写与消息投递。

一期不接入 Collector，仅要求 `trace_id` 贯穿两个进程的日志。前提是租户上下文通过 `context.Context` 全链路传递，该约束在一期即需满足。

## 8. 不在交付范围内

| 项 | 说明 |

| 流式响应 | IM 通道无长连接，只能通过分段推送或消息编辑模拟，且与平台限流冲突。验收标准未要求，不做。仅保留一处写法约束：Worker 逐个 Event 交给输出函数处理，不攒完再返回 |
| tRPC-Go RPC | 见第 4 节 |
| 沙箱与 Skill | 现有 `workspace`、`skill` 包保留，本期不实现 |
