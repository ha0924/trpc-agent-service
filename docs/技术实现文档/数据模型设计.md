# 数据模型设计

本文说明平台的表清单与各表用途，并给出一期落地的表结构。

## 1. 全表清单

共 26 张，按职责分六组。★ 为一期建表，共 12 张，见 `docs/action/一期/一期表结构.md`。

### 1.1 租户与配置

| 表 | 用途 |
|---|---|
| ★ `tenants` | 租户本身，隔离边界。`settings` 装租户级策略：预算、限流、模型白名单、脱敏规则 |
| ★ `agent_apps` | 租户下有哪些 Agent，如客服、运维、数据分析 |
| ★ `agent_versions` | 某一版的 Prompt 与模型配置，发布后不可修改 |
| ★ `agent_deployments` | 当前环境使用哪个版本及灰度权重，回滚即修改此表 |

### 1.2 能力定义与授权

定义表跨版本共享，绑定表按版本冻结，随版本一同回滚。

| 表 | 用途 |
|---|---|
| `tool_definitions` | 平台提供哪些 Tool |
| ★ `agent_tool_bindings` | 某个版本可用哪些 Tool，取值 allow / deny / ask |
| `extension_definitions` | Plugin、Guardrail、Callback 的定义，由 `kind` 区分 |
| ★ `agent_extension_bindings` | 某个版本启用哪些扩展及其参数 |
| `mcp_servers` | 租户接入了哪些 MCP 服务 |
| ★ `agent_mcp_bindings` | 某个版本使用哪几个 MCP 服务 |
| `knowledge_bases` | 租户有哪些知识库，各指向哪个向量库 |
| `agent_knowledge_bindings` | 某个版本挂载哪几个知识库 |
| `skills` | 租户的 Skill 工作流 |
| ★ `agent_skill_bindings` | 某个版本挂载哪些 Skill |

Tool、扩展、MCP、Skill 四类能力配置以绑定表存放，不并入 `agent_versions` 的单列 JSON。这四类均为不定长列表且会持续增长，合并存储会使该列不断膨胀，而每次装配 Runtime 都需整列读出并解析。拆表带来的多次查询由 Runtime 缓存吸收——版本不可变，缓存不失效，查询只发生在首次装配。Prompt 与模型配置是一个版本恰好一份的定长配置，因此仍作为 `agent_versions` 的列。

Plugin、Guardrail、Callback 的实现在代码中注册，表中只记录启用项与参数，Runtime 装配时读表挂载。因此新增一种扩展只需注册实现，不改装配逻辑，也不改表结构。

### 1.3 通道与身份

| 表 | 用途 |
|---|---|
| ★ `channel_bindings` | IM 账号绑定到哪个租户的哪个 Agent，并记录通道能力描述符 |
| `channel_users` | 外部 IM 用户映射为内部用户 |

### 1.4 运行数据

| 表 | 用途 |
|---|---|
| ★ `sessions` | 会话元数据，固化创建时选定的 Agent 版本 |
| ★ `session_events` | 会话内的每条消息与每次 Tool 调用，带 `sequence` 保序 |
| ★ `inbound_events` | 入站幂等记录与执行、投递状态机，同时是在途请求的可靠记录 |
| `session_summaries` | 长会话的历史摘要 |
| `memories` | 跨会话长期记忆 |

### 1.5 后端路由

| 表 | 用途 |
|---|---|
| `backend_configs` | 平台接入了哪些后端实例，一行一个数据库或存储 |
| `backend_bindings` | 某类数据走哪个后端实例，即 Storage Router 的路由依据 |

拆为两张表的原因是同一个后端实例会被多个租户、多种数据类型共用。若合为一张，连接信息需在每条绑定中重复，且更换密钥要改动多行。拆开后 `backend_configs` 表达"有哪些后端"，`backend_bindings` 表达"谁用哪个"，新增租户只增加绑定记录。

### 1.6 审计与治理记录

运行时产生的记录，性质上不属于配置。

| 表 | 用途 |
|---|---|
| `tool_approvals` | 危险 Tool 的二次确认记录 |
| `audit_logs` | 谁、何时、经由哪个通道、使用哪个 Agent 或 Tool、系统允许还是拒绝 |
| `usage_records` | Token 与成本明细 |

### 1.7 不落表的两项

- **密钥**：明文保存在 Secret Manager，库中只存 `secret://` 形式的引用，分散于 `channel_bindings.secret_ref`、`backend_configs.dsn_ref` 与版本配置中；
- **预算计数器**：`usage_records` 是明细，用于对账。判断租户是否超额不能实时 `SUM` 明细，且多个 Worker 并发扣减需要原子操作，因此计数器放 Redis 按租户与周期累加。若缺少这一项，预算限制会退化为只统计不拦截。

## 2. 通用约定

- 物理主键统一为自增 `BIGINT UNSIGNED`，业务标识另立 `VARCHAR` 唯一键。业务标识用于跨进程传递与日志，不暴露自增值；
- 除 `tenants` 外所有表携带 `tenant_id`，且索引以 `tenant_id` 起头，保证租户维度查询走索引；
- 枚举值使用 `VARCHAR` 而非 `ENUM`，便于后续增加取值而不改表结构；
- 不使用外键约束，关联关系由应用层保证，避免后续分库与跨后端受限；
- 关键表预留 JSON 扩展列，新增可选属性不改表；
- 表示"租户级默认"时使用空串而非 `NULL`，因 MySQL 唯一键不约束 `NULL`；
- 字符集 `utf8mb4`，时间列统一 `DATETIME(3)`。

## 3. 与 Redis 的分工

`sessions` 表存会话的长期元数据：所属租户与 Agent、创建时固化的版本、外部标识映射、最后活跃时间。会话的短期上下文即 Session State 存 Redis，Session 租约与信箱同样存 Redis。

`session_events` 是全量历史，属体量最大的表，落 MySQL。

## 4. 扩展位置

| 扩展方向 | 位置 |
|---|---|
| 租户级预算与限流 | `tenants.settings` |
| Agent 模型调用参数 | `agent_versions.model_params` |
| Tool 的版本级覆盖配置 | `agent_tool_bindings.params` |
| 扩展参数 | `agent_extension_bindings.params` |
| 更精细的灰度规则 | `agent_deployments.strategy` |
| 通道能力差异 | `channel_bindings.capabilities` |
| 用户角色与权限判断 | `channel_users.attributes` |
| 新增数据类型与后端 | `backend_bindings.data_type` 取值 |
