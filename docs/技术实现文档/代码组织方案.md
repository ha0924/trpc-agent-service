# 代码组织方案

本文说明实现阶段的代码组织方式：仓库如何划分、包如何分层、依赖方向如何约束。不涉及具体函数与字段设计。

## 1. 技术栈

| 位置 | 选型 | 说明 |
|---|---|---|
| Agent 框架 | tRPC-Agent-Go | 提供 Agent 编排、Runner、Tool、Session 等能力 |
| Web 框架 | Gin | 仅 Gateway 侧使用，承载通道回调与后续 Admin API |
| 配置与业务库 | MySQL | 租户、Agent 版本、发布、通道绑定、审计等 |
| 运行时状态 | Redis | Session、Session 租约、Session 信箱 |
| 消息队列 | 待定 | 一期先用 Redis List 顶替，通过接口隔离 |

不引入 tRPC-Go RPC 框架。Gateway 与 Worker 之间通过消息队列和共享存储通信，不存在互相调用的 RPC 关系，引入 RPC 框架不产生收益。

流式响应不在交付范围内。仅保留一处写法约束：Worker 消费 Runner 的 Event 通道时逐个 Event 交给一个输出函数处理，不一次性攒完再返回，以便后续扩展。

## 2. 仓库与进程

一个仓库、一个 Go module，编译出两个可执行文件。

```text
cmd/gateway   Gateway 进程
cmd/worker    Worker 进程
```

两者独立部署、独立扩缩容，但共用统一消息模型、租户上下文、配置读取、存储路由与调度库，因此不拆分仓库。

跨进程协作只依赖两条通路：

```text
消息队列：Gateway 投递待处理提示，Worker 消费
共享存储：Redis 与 MySQL，两侧各自读写
```

## 3. 分层方式

分层发生在进程内部，共享部分上提为公共包。

```text
接口层    Gateway 的 HTTP Handler；Worker 的队列消费循环
业务层    租户识别与路由、Runtime 装配、租约调度、一轮 Agent 执行
模型层    统一消息、租户上下文、配置实体、Session 与 Event
```

模型层与存储访问由两个进程共享，业务层与接口层各自独立。

不采用领域模型分层。本系统的复杂度集中在进程划分、队列、租约与后端路由等基础设施，业务规则本身很薄，引入领域建模只增加负担。

## 4. 包结构

包划分与系统架构图的分层一一对应，便于从图定位代码。

```text
cmd/
  gateway/                Gateway 入口
  worker/                 Worker 入口

trpcservice/
  types/                  统一消息模型、租户上下文、核心接口定义
  config/                 配置读取，对应控制面的配置发布
  tenant/                 租户模型与隔离判断
  channels/               接入适配层，Channel 实现与能力描述符
  gateway/                网关层业务逻辑：租户识别、Agent 与版本路由、入站幂等
  scheduler/              Session 租约与信箱，Gateway 与 Worker 共用
  agent/                  Runtime 装配，按 tenant 与 version 构建 Runner
  storage/                Storage Router 与各后端适配
  tool/                   平台 Tool 与租户级 Tool 注册
  log/                    日志与脱敏
  metrics/                指标与埋点
  skill/                  Skill 能力，一期不动
  workspace/              沙箱工作目录，一期不动
  web/                    管理与对话页面，二期起用
```

其中 `types`、`gateway`、`scheduler`、`storage` 为新增包。原有目录取自项目 README 的示例结构，该结构基于单进程视角，未包含调度与存储路由的位置。

`agent` 包的职责调整为 Runtime 装配，而非存放具体 Agent 定义。Agent 的 Prompt、模型、Tool 等均来自配置库中的 Agent Version，由该包在运行时装配。

## 5. 依赖方向

```text
cmd/gateway → trpcservice/gateway  ┐
cmd/worker  → trpcservice/agent    ┴→ scheduler / storage / config / channels → types
```

约束两条：

- `types` 不依赖任何其他内部包，所有包可依赖它；
- `gateway` 与 `agent` 之间不互相依赖，两者的协作只通过队列与共享存储发生。

## 6. 实现顺序

`types` 先落地。统一消息模型、租户上下文与四个核心接口确定后，其余包即可并行开发，互不阻塞。

四个核心接口：

| 接口 | 职责 | 一期实现 |
|---|---|---|
| `Channel` | 消息收发与通道能力描述 | Mock 通道，HTTP 收发 |
| `SessionDispatcher` | 投递与消费待处理提示 | Redis List |
| `StorageRouter` | 按 `tenant + agent + data_type` 选择后端 | 仅注册 Session 一路，走 Redis |
| `RuntimeProvider` | 按 `tenant + version` 装配 Runtime | LLMAgent 加两个 Tool |

## 7. 一期的层级取舍

原则：架构图上的**框**可以只做一个，架构图上的**箭头**必须全部打通。

| 架构图分层 | 一期范围 |
|---|---|
| 外部消息源 | 仅 HTTP 一路，IM 与 AG-UI、A2A 不做 |
| 接入与适配 | Channel 仅 Mock；统一消息模型、身份映射、入站幂等均需落地 |
| 网关与调度 | 租户识别、Agent 与版本路由、租约与信箱均需落地；鉴权限流不做 |
| Agent 执行层 | 单副本运行，但需保证多副本并行无冲突 |
| 框架能力 | 仅 LLMAgent 与两个 Tool，Graph、MCP、Guardrail 不做 |
| 共享存储层 | Storage Router 需真实路由，下游仅接 Session 一路 |
| 平台控制面 | 配置表建好并写入一条数据，Worker 从配置库读取；Admin API 不做 |
| 可观测层 | 仅 `trace_id` 贯穿日志，Collector 与 Metrics 不做 |

两处一期不可省略：Gateway 与 Worker 必须是两个进程且中间隔着队列；Runtime 必须由配置驱动装配。二者决定了整体代码组织，后期补齐等同重写。
