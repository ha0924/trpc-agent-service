# 风险清单

本文列出平台上线后的主要生产风险及缓解措施。风险按影响面与发生概率分级，`高` 表示可导致数据错误、资金损失或跨租户泄漏，`中` 表示导致服务降级或个别会话不可用。

## 汇总

| # | 风险 | 类别 | 等级 | 核心缓解手段 |
|---|---|---|---|---|
| 1 | Session 租约过期后并发执行同一会话 | 一致性 | 高 | 持续续期 + 续期失败即放弃 + `uk_seq` 兜底 |
| 2 | 有副作用 Tool 被重复执行 | 一致性 | 高 | 操作幂等键 + 结果不确定不重试 + 审计前置 |
| 3 | 跨租户数据串用 | 安全隔离 | 高 | 缓存键强制含 `tenant_id` + 存储层统一注入租户条件 |
| 4 | 密钥泄漏到日志、Trace 或 Prompt | 安全 | 高 | 只存引用 + 统一 Redactor + 禁入 Trace 属性与 Metric 标签 |
| 5 | 毒消息阻塞 Session 信箱 | 可用性 | 中 | 单条重试上限 + 死信隔离 + 继续排空信箱 |
| 6 | 模型超时、限流或配额耗尽 | 可用性 | 中 | 超时控制 + 有限重试 + 备用模型 + 熔断 |
| 7 | 存储短暂不可用导致幂等判断失效 | 一致性 | 高 | 状态不确定时不执行（fail-closed） |
| 8 | Runtime 缓存无上限导致 Worker OOM | 容量 | 中 | 容量上限 + LRU + `idle_ttl` |
| 9 | 出站凭据并发刷新互相顶掉 | 可用性 | 中 | 分布式锁 + 提前刷新 + 按绑定隔离缓存 |
| 10 | IM 平台限频导致回复堆积或丢失 | 可用性 | 中 | 按绑定限流排队 + 投递成功率监控 |
| 11 | goroutine 泄漏与 Event 通道未排空 | 容量 | 中 | `context` 全链路 + 停机排空 + goroutine 数监控 |
| 12 | 长会话上下文膨胀导致成本失控 | 成本 | 中 | Summary 压缩 + 历史轮数上限 + 租户预算拦截 |

## 一致性与顺序

### 1. Session 租约过期后并发执行同一会话

**场景**　Worker A 持有某会话租约并正在执行一个耗时较长的请求（模型慢、Tool 慢或 MCP 阻塞），执行时间超过租约 TTL。租约自动过期后，Worker B 抢到同一会话的租约并开始处理后续消息，两个 Worker 同时读写同一会话。

**影响**　会话事件乱序、State 互相覆盖、上下文错乱。这是本架构最核心的正确性风险，因为顺序保证完全建立在租约之上。

**缓解**

- 持有租约期间**持续续期**，续期周期显著小于 TTL；
- **续期失败即主动放弃**：Worker 发现自己已失去租约时，立即停止写入并放弃当前轮次，而不是继续执行完；
- `session_events` 的 `uk_seq (session_id, sequence)` 作为最后一道防线——即使发生并发，相同 `sequence` 的第二次写入会在数据库层直接失败，产生错误而非错乱数据；
- 为超长执行设置总超时，避免执行时间无上限增长。

### 2. 有副作用 Tool 被重复执行

**场景**　队列是 at-least-once 分发，加之投递重试、Worker 故障恢复与 IM 重复投递，同一请求可能被执行多次。若 Tool 有副作用（下单、退款、发消息、修改配置），重复执行造成实际损失。

**影响**　资金损失或业务数据错误，且不可自动回滚。

**缓解**

- 有副作用的 Tool 必须接受**操作幂等键**，由平台按 `request_id` 与调用序号生成并透传，由下游业务系统保证同键只生效一次；
- Tool 调用**结果不确定时（超时、连接中断）不盲目重试**，转为标记待人工确认；
- 危险 Tool 的**审计记录必须写在副作用发生之前**，写审计失败则不执行；
- 入站幂等由 `inbound_events.uk_event` 在最前端拦截重复投递。

### 7. 存储短暂不可用导致幂等判断失效

**场景**　MySQL 抖动，幂等记录写入失败或查询超时，Gateway 无法判断当前事件是否已处理过。

**影响**　若此时选择「先执行再说」，会导致重复执行；若选择丢弃，则消息永久丢失。

**缓解**

- **状态不确定时不继续执行（fail-closed）**：幂等记录写入失败则不返回 ACK，让 IM 平台按其重试机制重投。宁可重投也不漏记，因为重投会被后续的幂等记录拦截，而漏记无法恢复；
- Session State 不可用时同样不执行，避免在无上下文的情况下产生错误回复；
- 幂等记录写入使用短超时并快速失败，不长时间占用 Gateway 连接。

## 安全与隔离

### 3. 跨租户数据串用

**场景**　两种典型路径：一是 Runtime 缓存键遗漏 `tenant_id`，不同租户使用相同 Agent 名称与版本号时命中彼此的 Runtime，导致模型、Tool、知识库与密钥混用；二是某处存储查询遗漏租户条件，读到其他租户的会话或记忆。

**影响**　跨租户数据泄漏，属最严重的合规事故。

**缓解**

- **Runtime 缓存键强制为 `tenant_id + agent_app_id + agent_version`**，在类型层面约束，不允许手工拼接字符串；
- 存储访问统一经过 Storage Router，由其从租户上下文中**自动注入租户条件**，而非依赖每个调用方记得加；
- 除 `tenants` 外所有表携带 `tenant_id` 且索引以其起头；
- 针对隔离编写专门测试用例：同名不同租户的 Agent、同一用户在不同租户下的会话。

### 4. 密钥泄漏到日志、Trace 或 Prompt

**场景**　模型 API Key、IM Token、数据库密码经由错误日志、Trace 属性、Metric 标签、异常堆栈或 Prompt 拼接进入可观测系统或模型侧。

**影响**　凭据泄漏，且可观测系统通常保留期长、访问面广，泄漏难以彻底清除。

**缓解**

- 配置库只保存 `secret://` 形式的引用，明文仅存于 Secret Manager；
- Worker 运行时按租户与用途读取，**只在内存中使用**，不写入任何持久化结构；
- 统一 Redactor 对 Authorization、Token、API Key、Password、数据库 DSN、Cookie 与个人信息脱敏；
- 明确禁止密钥进入：普通配置表、日志、Trace 属性、Metric 标签、错误报告、Prompt、Session 与 Memory；
- 上线前对日志与 Trace 做一次采样审查。

## 可用性

### 5. 毒消息阻塞 Session 信箱

**场景**　某条消息因内容异常或 Tool 缺陷导致每次执行都失败。信箱按顺序排空，该消息不断重试，其后所有消息全部卡住。

**影响**　单个会话完全不可用，且用户无任何反馈。

**缓解**

- 单条消息设置**重试上限**，超限后移入死信队列并标记 `inbound_events.state = failed`；
- 移入死信后**继续排空信箱**，不因一条消息阻塞整个会话；
- 向用户返回一条明确的失败提示，而非静默丢弃；
- 死信记录保留完整 `payload` 与 `trace_id`，供排查与重放。

### 6. 模型超时、限流或配额耗尽

**场景**　模型供应商侧超时、限流或账户配额耗尽，且通常在业务高峰期集中发生。

**影响**　大面积回复失败，且失败请求的重试会进一步加剧限流。

**缓解**

- 设置单次调用超时与总执行超时，超时通过 `context` 立即取消下游；
- **有限重试加退避**，不无限重试；
- 配置备用模型，主模型持续失败时切换；
- 对模型调用做熔断，连续失败达阈值后快速失败，避免请求堆积耗尽 Worker 并发；
- 租户级预算在调用前拦截，避免单租户耗尽共享配额。

### 9. 出站凭据并发刷新互相顶掉

**场景**　企业微信等通道的 `access_token` 有效期约 2 小时。多个 Worker 同时发现凭据过期并各自刷新，而部分平台的新凭据会使旧凭据立即失效，导致先取到的 Worker 持有已失效凭据。

**影响**　回复投递批量失败，且表现为间歇性，排查困难。

**缓解**

- 凭据缓存在 Redis，**按 `channel_binding_id` 隔离**；
- 刷新时加分布式锁，同一绑定同一时刻只有一个刷新者，其余等待复用结果；
- **提前刷新**（如剩余有效期不足四分之一时），不等到过期；
- 投递收到凭据失效错误时，强制刷新一次并重试该条投递。

### 10. IM 平台限频导致回复堆积或丢失

**场景**　平台侧对每应用、每会话的发送频率有限制。批量回复或长文本拆分为多条时容易触发。

**影响**　回复发送失败。此时 Agent 已执行完成，丢弃等于用户收不到任何回复。

**缓解**

- 按 `channel_binding_id` 在 Redis 中计数限流，**触发限流时排队而非丢弃**；
- 长文本按 `max_text_length` 在段落边界拆分，控制条数；
- 监控 IM 投递成功率，持续下降时告警；
- 失败投递按 `delivery_failed` 状态只重试投递，不重跑 Agent。

## 容量与成本

### 8. Runtime 缓存无上限导致 Worker OOM

**场景**　租户与 Agent 版本持续增长，Worker 按需装配并缓存 Runtime。由于已发布版本不可变、缓存永不失效，若无淘汰机制则缓存只增不减。每个 Runtime 持有模型客户端、Tool、MCP 连接等资源，内存占用不低。

**影响**　Worker 内存耗尽被杀，且重启后重新装配会形成雪崩。

**缓解**

- 设置缓存**容量上限并按 LRU 淘汰**；
- 配置 `idle_ttl`，长时间未使用的 Runtime 主动释放；
- 释放时正确调用 `Close()`，回收 MCP 连接与后台任务；
- 埋点 `runtime_cache_hit_rate`、`runtime_build_latency_p95`、`mcp_conn_count`，据此确定容量参数；
- 正在执行的请求完成后才释放对应 Runtime。

### 11. goroutine 泄漏与 Event 通道未排空

**场景**　Runner 返回的 Event 通道在请求取消后未被消费完，或后台重试任务没有明确退出条件，goroutine 持续累积。

**影响**　内存与调度开销缓慢增长，通常在运行数天后才显现，难以定位。

**缓解**

- `context.Context` 从 Gateway 贯穿到模型、Tool 与存储，任何一处签名缺失都会导致取消无法传递；
- 每个 goroutine 有明确退出条件，后台任务使用受控的 Worker Pool 而非裸 `go`；
- **Runner 的 Event 通道必须持续消费到关闭**，即使已决定放弃本次结果；
- Worker 停机顺序：停止消费新消息 → 等待在执行请求 → 超时后取消 → 排空 Event 通道 → 关闭资源 → 退出；
- 监控 goroutine 数量与内存趋势，设置增长告警。

### 12. 长会话上下文膨胀导致成本失控

**场景**　IM 会话往往长期存在，历史消息不断累积。若每次调用都携带全部历史，token 消耗随会话长度线性增长。

**影响**　成本快速上升，且上下文超限后直接调用失败。

**缓解**

- 启用 Summary 压缩历史，只保留最近若干轮完整消息；
- 设置历史轮数上限与上下文压缩阈值；
- 租户级日、月预算计数器存于 Redis，**超额时拦截而非仅统计**——预算判断不能实时 `SUM` 明细表，且多 Worker 并发扣减需要原子操作；
- 按租户记录 `usage_records` 明细供对账，与实时计数器分工。

## 其他已知约束

以下项已在设计中处理，列出以备评审对照：

| 项 | 处理方式 |
|---|---|
| 消息队列丢消息 | 队列契约本就不要求可靠。`inbound_events` 是在途请求的可靠记录，扫描长时间处于 `processing` 的记录即可补偿 |
| 灰度权重配置错误 | 一行一环境、权重存于单个 `routes` JSON，更新天然原子，不存在权重和不为 100 的中间态；写入时另做校验 |
| 版本回滚导致能力配置不一致 | 四张绑定表与 `agent_versions` 同为不可变数据，回滚版本即回滚能力配置 |
| Worker 故障 | 无需通知机制，租约 TTL 到期自动释放，其他 Worker 接管。**租约 TTL 即故障恢复时间** |
| 后端迁移数据丢失 | 采用全量复制 → 增量同步 → 校验 → 切换绑定 → 保留回滚窗口 |
