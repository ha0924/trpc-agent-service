# 框架复用与扩展

本文说明平台哪些能力**直接复用** tRPC-Agent-Go，哪些必须**新增平台层模块**，以及每处扩展的理由。

结论基于对 `trpc-agent-go v1.11.2` 与 `openclaw v0.0.1` 的源码核对，而非文档描述。

## 1. 框架的模块结构

tRPC-Agent-Go 是**多模块仓库**。核心模块只包含无重依赖的部分，各存储后端与工具拆为独立 Go module，需单独引入：

| 模块 | 版本 | 内容 |
|---|---|---|
| `trpc-agent-go` | v1.11.2 | agent、runner、model、tool、plugin、session（仅 inmemory / noop）、knowledge、memory、telemetry、server |
| `session/redis` `session/mysql` `session/postgres` | v1.11.0 / v1.11.2 / v1.11.0 | Session 持久化后端 |
| `storage/redis` `storage/mysql` `storage/s3` `storage/qdrant` | v1.11.0 | 通用存储适配 |
| `memory/redis` | v1.11.0 | Memory 后端 |
| `server/agui` | v1.11.0 | AG-UI 服务化 |
| `openclaw` | **v0.0.1** | OpenClaw 形态的常驻 Runtime 应用 |

需要注意的是核心模块的 `session/` 下**只有 `inmemory` 与 `noop`**，Redis 与 SQL 后端必须额外引入对应子模块。这一点直接影响多后端支持的依赖组织。

`openclaw` 仅有 v0.0.1，其 `go.mod` 中对同仓其他模块使用 `replace ... => ../` 相对路径。该指令仅在主模块生效，外部依赖时失效，实际解析走 `require` 中声明的 v1.8.0，再经 MVS 与我们显式引入的 v1.11.2 取最大值。同主版本号，可正常共存。

## 2. 直接复用的能力

### 2.1 Agent 编排与执行

| 能力 | 复用方式 |
|---|---|
| `agent.Agent` 接口 | 装配结果一律返回该接口，不返回具体类型 |
| `agent/llmagent` | 一期唯一使用的 Agent 类型，60+ 个 Option 支持配置驱动装配 |
| `agent/graphagent`、`chainagent`、`parallelagent`、`cycleagent` | 后续编排能力，装配时多一个分支即可接入 |
| `runner.Runner` | 执行入口，`WithSessionService` 支持注入自定义 Session 服务 |

`llmagent` 的 Option 覆盖了平台装配所需的全部维度——`WithModel`、`WithInstruction`、`WithTools`、`WithGenerationConfig`、`WithAgentCallbacks`、`WithModelCallbacks`、`WithExtensions`、`WithKnowledge`、`WithPlanner` 等。**配置驱动装配不需要绕过框架或自建构造路径。**

### 2.2 治理挂载位

`plugin.Registry` 提供九个挂载点，覆盖了平台全部治理需求：

| 挂载点 | 平台用途 |
|---|---|
| `BeforeAgent` / `AfterAgent` | IM 用户与角色权限校验 |
| `BeforeModel` / `AfterModel` | 输入输出脱敏、预算与 Token 限制 |
| `BeforeTool` / `AfterTool` | Tool 白名单、危险 Tool 拦截与二次确认 |
| `AfterToolMessages` | Tool 结果脱敏 |
| `OnEvent` | 事件级审计与指标 |
| `AfterRun` | 成本统计、Usage 记录 |

`plugin.Plugin` 接口只有 `Name()` 与 `Register(*Registry)` 两个方法，形状恰好适配「按配置动态挂载」——平台从 `agent_extension_bindings` 读出启用列表，按 `priority` 排序后依次 `Register`。

框架的 `plugin/guardrail` 下另有 `approval`、`promptinjection`、`unsafeintent` 三个内置实现，其中 `approval` 直接对应「危险 Tool 二次确认」需求。

**平台不自建 hook 机制，不绕过这些挂载位直接调用模型。**

### 2.3 Tool

`tool/function.NewFunctionTool[I, O](fn, opts...)` 以泛型方式从普通 Go 函数构造 Tool，JSON Schema 自动生成。`tool/` 下另有 30 余个内置包（`mcp`、`file`、`webfetch`、`duckduckgo`、`permission` 等）可按需引入。

平台不重新发明 Tool 抽象，只新增租户维度的注册与白名单。

### 2.4 存储后端

Session 的 Redis、MySQL、PostgreSQL 后端由框架子模块提供，平台**不自行实现存储层**，只做租户级路由（见 3.3）。

### 2.5 openclaw 中可复用的部分

openclaw 的包分为公开与 `internal` 两类，后者在 Go 语言层面禁止外部模块引用：

| 公开（可引用） | 内容 |
|---|---|
| `openclaw/channel` | Channel 最小接口 |
| `openclaw/gwproto` | 网关协议消息类型 |
| `openclaw/plugins/telegram` | **仅 204 行的注册薄壳**，协议实现在 `internal/`，见下方说明 |
| `openclaw/registry` `delivery` `conversation` `subagent` `admin` `gwclient` | 扩展注册、投递标注等 |

| `internal`（**不可引用**） | 内容 |
|---|---|
| `openclaw/internal/gateway` | **Gateway 服务器本体** |
| `openclaw/internal/{channel,telegram,outbound,uploads,pairing,persona,skills,cron}` | 各能力内部实现 |

**关于 `plugins/telegram` 的更正（实测）**：此表初版把它记为「一个完整的 Channel 实现」，据此推断接 Telegram 可以复用现成代码。**这个推断是错的。**

该文件只有 204 行，做的是配置解析与注册，真正的协议实现 `import` 了两个 internal 包：

```go
tgch  "trpc.group/trpc-go/trpc-agent-go/openclaw/internal/channel/telegram"
tgapi "trpc.group/trpc-go/trpc-agent-go/openclaw/internal/telegram"
```

Go 在语言层面禁止外部模块引用 `internal/`，因此**接 Telegram 必须自己实现 Bot API 协议**，可复用的只有 `channel.Channel` 接口本身。这与企业微信是自研的原因相同，不是「一复用一自研」，而是两个都得自研。

结论：**openclaw 里可复用的只有类型与接口，没有任何可复用的通道实现。**

两处复用重点：

**`openclaw/channel`** —— 平台 Channel 接口内嵌它，坐实「复用并扩展」：

```go
type Channel interface {
    openclawchannel.Channel   // ID() / Run()
    // 平台扩展：验签、解码、ACK、能力描述
}
```

内嵌把 `Run(ctx) error` 一并收了进来，而它一度是死代码：三个通道都实现为 `<-ctx.Done()`，全仓零调用点。长连接模式落地后它成为真实调度点——Gateway 为 `inbound_mode=stream` 的绑定启动 `Run()`，由通道主动向 IM 平台建连收流。这是内嵌带来的收益之一：预留位置由编译器保证存在，补实现时不需要改接口。

**`openclaw/gwproto`** —— 已定义 `MessageRequest`、`MessageResponse`、`Usage`、`StreamEvent` 以及 `ContentPart` 的各变体（`ImagePart`、`AudioPart`、`FilePart`、`LocationPart`、`LinkPart`）。平台统一消息模型直接基于其 `ContentPart`，富媒体类型不必重新定义。

## 3. 必须新增的平台层

### 3.1 Gateway 与调度

openclaw 的 Gateway 位于 `internal/`，语言层面无法引用。但即便可引用也必须重写，因为它与多租户平台的需求有三处根本冲突：

| openclaw 的做法 | 局限 | 平台的扩展 |
|---|---|---|
| `POST /v1/gateway/messages` **同步返回 reply** | IM 通道有秒级响应超时，长任务必然超时 | 立即 ACK + 队列 + 主动推送 |
| 同一 session 串行靠**进程内锁** | 单进程有效，多副本失效 | Redis **跨节点**租约 + 信箱 |
| `session_id = <channel>:dm:<from>` | **无租户维度** | `tenant + channel_binding + scope + scope_key` |
| allowlist 与 mention gating 走**命令行 flag** | 全局配置，不分租户 | 租户级配置，由配置库下发 |
| 单 Agent，启动时命令行装配 | 写死一个 Agent | 按 `tenant + version` 配置驱动装配 |

openclaw 的定位是**单用户常驻助理 Runtime**，平台的定位是**多租户服务**。前者的每一处简化在后者场景下都不成立，因此 Gateway 与 Scheduler 是平台层新增，而非复用。

### 3.2 Worker 与 Runtime 装配

框架提供 `runner.Runner` 与 `llmagent`，但不提供「按租户与版本从配置库装配 Runtime 并缓存」这一层。平台新增：

- `RuntimeProvider`：按 `tenant + agent_app + version` 读取五张表并装配；
- Runtime Registry：按同一三元组缓存，含容量上限与 `idle_ttl`；
- 队列消费循环与租约管理。

### 3.3 Storage Router

框架的 `session.Service` 是一个约 15 个方法的接口（`CreateSession`、`GetSession`、`ListSessions`、`DeleteSession`、`AppendEvent`、`UpdateSessionState`、`UpdateAppState`、`UpdateUserState` 等）。

平台的 Storage Router **实现该接口**，内部按 `tenant + agent + data_type` 路由到不同的后端实例，再经 `runner.WithSessionService(router)` 注入：

```text
Runner → session.Service（平台 Router）→ 按租户选择 → session/redis 或 session/mysql
```

这样多后端路由天然嵌入框架执行路径，不需要在框架之外另造一层数据访问抽象。代价是需要实现全部委托方法。

### 3.4 其余平台层模块

| 模块 | 原因 |
|---|---|
| 租户模型与配置管理 | 框架无租户概念 |
| Channel 的验签、解密、幂等、身份映射 | `openclaw/channel` 只有 `ID()` 与 `Run()` |
| 企业微信 Channel 实现 | 框架与 openclaw 均未提供 |
| 租户级 Guardrail 策略实现 | 框架提供挂载位，不提供具体策略 |
| 租户维度的审计、Usage 与成本统计 | 框架提供 Telemetry 埋点，不提供租户账本 |
| Admin API | 框架无配置管理面 |
| Secret Reference 解析 | 框架不涉及密钥管理 |

## 4. 对照总表

| 平台需求 | 直接复用 | 平台层新增 |
|---|---|---|
| Agent 编排 | `agent/llmagent`、`graphagent`、Chain / Parallel / Cycle | 租户级注册、发布与版本路由 |
| 执行入口 | `runner.Runner` | Worker 调度、租约、无状态水平扩展 |
| Session / Memory / Artifact / Knowledge | `session/*`、`memory/*`、`artifact`、`knowledge` 及各后端子模块 | 租户级后端选择、`session.Service` 路由实现、迁移 |
| Tool / MCP / Skill | `tool/function`、`tool/mcp`、`skill` | 租户白名单、密钥注入、危险 Tool 审批 |
| 治理 | `plugin.Registry` 九个挂载点、`plugin/guardrail` 内置实现 | 租户策略下发、预算账本 |
| 服务化 | `server/openai`、`server/agui`、`server/a2a` | 统一 Gateway、Admin API |
| IM 接入 | `openclaw/channel` 接口、`openclaw/gwproto` 消息类型、`plugins/telegram` | 企业微信通道、验签幂等、租户绑定 |
| 可观测 | OpenTelemetry tracing / metrics | 租户维度审计、成本与合规 |

## 5. 版本与稳定性

| 依赖 | 风险 | 应对 |
|---|---|---|
| `trpc-agent-go` v1.11.2 | 主版本稳定 | 正常引用 |
| 各后端子模块 v1.11.x | 与核心同步发布 | 正常引用 |
| **`openclaw` v0.0.1** | **版本号表明 API 未稳定** | 只引用 `channel` 与 `gwproto` 两个小而稳定的包；不依赖其 `app` 与 `internal` 实现。即便其后续发生破坏性变更，影响面也限于接口内嵌与消息类型两处 |

平台的 Channel 接口内嵌 openclaw 接口而非复制其定义，因此复用关系在编译期可验证；同时平台自身的扩展方法不受其变更影响。

### 5.1 依赖 openclaw 会把核心框架降级（实测）

openclaw v0.0.1 的 `go.mod` 中 `require trpc.group/trpc-go/trpc-agent-go v1.8.0`。若主模块没有**直接**依赖核心框架，`go mod tidy` 会按 MVS 把核心框架解析为 v1.8.0，而非我们期望的 v1.11.2：

```text
go get trpc-agent-go@v1.11.2      # go.mod 写入 v1.11.2
go get openclaw@v0.0.1
go mod tidy                        # ← 此处被降级
go list -m trpc-agent-go           # 输出 v1.8.0
```

降级的后果不是编译失败，而是**编译到了不同的 API**。例如 v1.11.2 的 `model.File` 有 `URL` 字段而 v1.8.0 没有，表现为「源码里明明有这个字段，编译器却说不存在」，极易误判为自己写错。

规避方式：保证主模块**有代码直接 import 核心框架的包**。`trpcservice/types` 同时 import 了 `agent`、`model`、`runner`、`session`，因此核心框架是真实的直接依赖，`tidy` 不会再降级。

这条同时也是「只引用 `channel` 与 `gwproto` 两个小包」这一决策的补充理由：依赖面越小，被 openclaw 的版本约束拖动的风险越低。

### 5.2 `frametrace.TracerProvider` 不会被 `Start` 更新（实测）

`telemetry/trace.Start()` 内部通过 `otel.SetTracerProvider()` 安装 provider，但它自己导出的包级变量 `frametrace.TracerProvider` **始终是初始的 noop，从未被重新赋值**：

```go
// 框架源码 telemetry/trace/trace.go
var TracerProvider trace.TracerProvider = noop.NewTracerProvider()  // 第 36 行
...
otel.SetTracerProvider(tracerProvider)                              // 第 334 行，设的是全局
Tracer = otel.Tracer(itelemetry.InstrumentName)                     // 第 86 行，只更新 Tracer
```

因此 `frametrace.TracerProvider.Tracer(name)` 拿到的是空实现，**它产生的 span 会被静默丢弃**。

症状极具迷惑性：框架自身的 span（`invoke_agent`、`chat`）能正常上报，因为框架内部走的是 OTel 全局；而平台自己创建的 span 全部消失。看起来像是「埋点没生效」，实际是 tracer 取错了来源。

正确做法是从 OTel 全局取：

```go
p.tracer = otel.Tracer(tracerName)   // 而非 frametrace.TracerProvider.Tracer(...)
```

这个问题只有把真实 OTLP 上报打出来看才会暴露——单元测试里我们自建 SDK provider，是通过的。
