## 二、逐项：做了什么，以及为什么这么做

### 1. 管理面写入（A2–A4、A6、A8、A11）

任务描述第一句是「平台需要支持多个租户**创建和部署**自己的 Agent」。此前「部署」有了（灰度权重可改），「创建」全部只能手写 SQL——Admin API 13 个端点里只有 2 个是写。

现在 30 个端点，生命周期是「建租户 → 建 Agent → 建版本（草稿）→ 配工具与治理 → 发布 → 配权重」。

两处设计取舍：

- **已发布版本不可改由 SQL 保证**（`UPDATE ... WHERE status = 'draft'`），不是靠约定。Go 侧的检查在并发下有竞态窗口，而这是「缓存的 Runtime 永不过期」的前提；
- **绑定列表整组替换而非增量**。列表本身就是权限授予，增量更新会留下「Agent 持有谁也没批准过的工具集」的窗口；在已发布版本上，那个窗口就是权限提升。

### 2. 审计策略（A1、A10）—— 租户模型第 7 要素

按租户配置审计里能留多少原文，四种 `body_mode`：`full` / `truncate` / `hash` / `drop`。

必须按租户配是因为诉求相反：受监管行业要留证据以便复查，注重隐私的租户要求正文一律不落库、只留哈希。写死任何一种都会让另一类租户无法使用。

三点刻意为之：

- **缺行时用安全默认（truncate）而非 full**。否则这个功能一上线，就会开始记录所有既有租户的完整正文；
- **凭据脱敏不受此策略影响**，`redact_level=none` 也不例外——租户不能给自己开权限去泄漏平台的密钥；
- **在 `WriteAudit` 单一收口处生效**，不在各调用点。靠约定执行的规则，总会在最关键的那个调用点被忘记。

### 3. 危险工具审批（F5）—— 从「有表零调用」到真的能放行

**这一项的记录被修正过两次，过程本身值得留下。**

初记「缺审批通道」→ 核实后发现更弱：`tool_approvals` 的表、DDL、`CreateToolApproval`、`ResolveToolApproval` 全都写好，**但两个函数零调用点**，`approval_id` 只在 `audit_logs` 的 JSON 里。这是本项目第四次栽在「函数存在、零调用点」上。

现在一次受控调用走两轮：查无审批 → 落表并拒绝 → 人工经 Admin 放行 → 用户再次请求 → 原子领用 → 执行。

**不能一轮完成**：在回调里阻塞等人决策会占住 Worker 槽位与会话租约，而租约会在等待中过期并把会话交给另一个 Worker。

三处设计决定，每处对应一种做错的方式：

- **新增 `consumed` 状态**，使一次审批只买一次执行。没有它，guardrail 会一直查到那条 approved 记录并一直放行——审批一次就永久关闭了闸门，**比没有闸门更危险，因为它看起来还在**；
- **新增 `args_fingerprint`**，把审批绑定到被审的那组参数。没有它，批准「删除订单 123」会顺带授权「删除订单 999」；
- **领用是单条原子 UPDATE**，不是先读后判。两个并发调用不能都看到 approved 然后都执行。

### 4. Memory 接通（D3、D8、D11）

此前多后端路由是真的，但流经它的只有 Session 一类，四个 `DataType` 常量使用点为 0。这是验收标准第 2 条的核心。

**隔离机制刻意复用而非另造**：`memory.UserKey.AppName` 承载 `tenant/agent`，与 session 的 app name 完全一致。两个租户各自用 `u1` 作用户 id 也会落到不同记忆。复用同一机制意味着可能发生跨租户泄漏的地方只有一处，不是两处。

**租户从数据本身取，不从 context 取**。框架会在自己的执行流里调用 memory 工具，那时调用可能已跨过携带派生 context 的 goroutine；app name 随数据走，不会像 context value 那样丢。

顺带修掉一个 Go 陷阱：typed nil 指针放进接口会让该字段非 nil，于是框架收到一个 nil 路由，每次记忆调用都 panic。装配处显式判空后再赋值。

### 5. 拆分入站与出站模式

`InboundMode` 此前同时承载两个问题：「消息怎么进来」与「回复怎么出去」。企业微信 aibot 恰好两者耦合——经 socket 收、也必须经同一条 socket 回——所以一个字段曾能同时描述对，**耦合看起来是固有的**。

Telegram 打破了这个巧合：long polling 主动拉取入站，但回复走普通 HTTPS，任意 Worker 都能发。

四种组合现在都能表达，其中两种此前根本说不出来：

| 入站 | 出站 | 例 |
|---|---|---|
| `payload` | `direct` | Mock、企业微信回调 |
| `stream` | `via_holder` | 企业微信 aibot |
| `stream` | `direct` | **Telegram**（此前无法表达） |
| `fetch` | `direct` | 微信客服 |

**单独一个提交，不与 Telegram 混做**：否则出问题时分不清是新通道的 bug 还是抽象改动的 bug。这个教训来自台账 §八 #10 #11。

### 6. Telegram 通道（E0、E5）

E0 分歧此前记为 ⚠️：`mock` 是平台自证，而企业微信的回调与长连接虽差异极大，却是同一平台的两种接入方式。现在是两个平台。

**协议自研，不是复用。** `openclaw/plugins/telegram` 看着像完整实现，实为 204 行注册薄壳，真正的协议在 `internal/` 下，Go 禁止外部模块引用。此前设计文档写「有现成实现可适配」是误判，已在 `框架复用与扩展.md` §2.5 更正。

三处非显然的实现决定：

- **游标即确认，故只在持久接受后推进。** 请求 offset N+1 就是在告诉 Telegram N 已完成。先推进会丢掉一条流水线拒收的消息，而此时已无平台侧重投可依赖；
- **错误里绝不带 URL。** token 直接出现在 URL 路径里，`net/http` 的错误会原文引用 URL。有一个测试专门锁这条；
- **编辑与 bot 消息一律忽略。** 把编辑当新消息会因用户改个错字而重跑 Agent、重复所有工具副作用。

### 7. 操作幂等键（I5）

风险清单 #2 评为高风险，把操作幂等键列为首要缓解手段。那一行的其余三项都已实现，**唯独键本身只存在于文字里**。

键由三者派生：`request_id`（跨重试相同）+ 调用序号（区分一请求内多次调用）+ 参数摘要（Agent 部分失败后重跑可能改变顺序，位置会撞）。

三处决定：

- **注入是选择性加入**（绑定里 `side_effect: true`）。给未声明的工具塞额外字段会让参数与 schema 不匹配，调用直接失败——安全特性变成故障源；
- **模型自带的 key 会被覆盖**。模型若能自选键值，就能通过在重试间改变它来绕过去重；
- **拿不到键就拒绝**。生成一个键会让每次重试都不同、匹配不到任何东西，等于没有保护。

### 8. 模型韧性（I4）

风险清单 #6 的四条此前只有第一条成立。

**最关键的一处限制，也是我写这段时最花时间的判断**：`model.Model` 返回的是 channel，因此**只能重试「读到第一个响应之前」的失败**。一旦有响应被转发出去，调用方可能已追加了半条 assistant 消息，重跑会为同一轮产生第二段不同的续写。中途失败原样透传。

这是真实限制而非疏漏，也是重试预算刻意设成 2 的原因：它覆盖连接被拒与立即 429,不覆盖生成到一半才死的供应商。

另三处：

- **未识别的错误默认不重试。** 分类靠文本匹配（框架无类型化错误分类），供应商改个措辞就会静默改变分类。宁可快速失败；
- **取消不计入熔断。** 否则一批用户取消会打开一个健康供应商的电路；
- **冷却后只放一个探针。** 一次性放开积压流量，会用正好压垮它的那个突发去打一个仍在恢复的供应商。

**熔断的目的不是保护供应商**（那是副作用），而是保护本平台：一个 30 秒超时的死供应商会让每个 Worker 槽位各占 30 秒。

## 四、刻意没做的，以及为什么

### C8 MCP 工具挂载 / C9 Skill 挂载

**都需要外部依赖，本机无法验证。**

- MCP：框架的 `mcp.NewMCPToolSet` 需要 `ConnectionConfig`（transport + server_url 或 command），而这些配置本该来自 `mcp_servers` 表——那张表未建。更关键的是，接完只能得到「代码写了但没连过任何 MCP 服务器」；
- Skill：框架的 `skill.Repository` 是文件系统实现（`FSRepository` + `SKILLS_ROOT` 环境变量），与平台「配置从数据库读」的模型不同，需要先设计租户级 Skill 存储如何映射到文件系统根目录。这是一个设计问题，不是一个接线问题。

硬做只能做出**第五个「有代码但没跑过」**——正是这个项目已经栽过四次的坑。

### D4 Summary —— 发现一处比「未实现」更值得记的事

原以为 Summary 是「有表无代码」。核实后发现更微妙：

1. `Router` **已经实现**了 `CreateSessionSummary` / `EnqueueSummaryJob` / `GetSessionSummaryText` 三个方法并正确按租户路由；
2. 框架的 `runner` **会自动调用** `EnqueueSummaryJob`（`runner.go:2531`）；
3. 但没有任何后端是**带 summarizer 构建的**——`session/redis` 等后端有 `WithSummarizer` 选项，平台从未传。

所以这三个方法每次调用都是**静默空操作**。这不是「没写代码」,而是第五个同类问题的雏形——只不过它还没被标成 ✅,所以没有造成误导。

**为什么不当场补上**：`summary.NewSummarizer(model, ...)` 需要一个模型，而每个租户的模型与凭据都不同。session 路由在启动时构建（`main.go:106`），那时还没有任何模型；用一个启动期模型给所有租户做摘要，等于用某一个租户的凭据去处理其他租户的会话内容——**这正是本平台最不能出的错**。

正确做法需要一处设计决定：让 summarizer 按租户延迟构建，或在装配 Runtime 时注入。这值得单独一个提交想清楚，不该塞在收尾里。已记入待验证清单。
