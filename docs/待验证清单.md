# 待验证清单

本文记录**已实现但我无法自行验证**的部分，以及需要你执行的命令。

写这份文档的原因：本项目已四次出现「代码写了但没接上」或「配置项存在却不生效」（见 [完成度台账.md](完成度台账.md) §八 #4 #7 #9 #12）。因此凡是我没有实际跑过的，一律不标「已完成」，而是列在这里等实测。

**沙箱限制**：Claude Code 的自动审批层拦截了两类操作，我试过多种写法均被拒，未绕过：

- MySQL 的**写**操作（建表、导种子数据）——读操作可以；
- 启动常驻进程（Gateway / Worker）。

因此所有需要建表或跑端到端脚本的验证都在此列。

## 三、已知缺口（我判断不该现在补的）

### `delete_order` 工具无实现

`seed_governance.sql` 里有一段注释掉的 `mode=ask` 绑定，因为 `delete_order` 这个工具在代码里没注册。F5 的端到端验证需要一个真实的 `ask` 模式工具。

**我没有加它**，理由：一个"删除订单"的假工具会让验收看起来更完整，但它不做任何事，属于为了让脚本变绿而造的道具。真实的 `ask` 工具应该在有真实副作用需求时才加。

如果你要验 F5 的完整链路，最小改动是把现有的 `calculator` 临时改成 `ask` 模式：

```sql
UPDATE agent_tool_bindings SET mode = 'ask'
 WHERE tenant_id = 'tenant-demo' AND tool_name = 'calculator';
```

验完改回 `allow`。这比造一个假工具诚实。

### Summary 的租户级 summarizer —— 一处需要设计决定的缺口

核实时发现的，比「未实现」更值得记：

1. `Router` **已实现** `CreateSessionSummary` / `EnqueueSummaryJob` / `GetSessionSummaryText` 并正确按租户路由；
2. 框架的 `runner` **会自动调用** `EnqueueSummaryJob`（`runner.go:2531`）；
3. 但没有任何后端是**带 summarizer 构建的**——`session/redis` 等有 `WithSummarizer` 选项，平台从未传。

所以这三个方法每次调用都是**静默空操作**。这是第五个同类问题的雏形，只不过它还没被标成 ✅，因此尚未造成误导。

**为什么不当场补**：`summary.NewSummarizer(model, ...)` 需要一个模型，而每个租户的模型与凭据都不同。session 路由在启动时构建（`cmd/worker/main.go:106`），那时还没有任何模型；用一个启动期模型给所有租户做摘要，等于**用某一个租户的凭据去处理其他租户的会话内容**——这正是本平台最不能出的错。

正确做法需要一处设计决定：让 summarizer 按租户延迟构建，或在装配 Runtime 时注入。值得单独一个提交想清楚。

### MCP 与 Skill 挂载

- **MCP**：`mcp.NewMCPToolSet` 需要 `ConnectionConfig`（transport + server_url 或 command），这些配置本该来自 `mcp_servers` 表——那张表未建。且接完只能得到「代码写了但没连过任何 MCP 服务器」；
- **Skill**：框架的 `skill.Repository` 是文件系统实现（`FSRepository` + `SKILLS_ROOT`），与平台「配置从数据库读」的模型不同，需要先设计租户级 Skill 存储如何映射到文件系统根目录。这是设计问题，不是接线问题。

两者硬做都只能做出第五个「有代码但没跑过」。
