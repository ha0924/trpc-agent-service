## 四、已跑通的链路

### 主链路

```text
发消息（curl 或控制台）
  → Gateway 按 webhook_path 查库确定租户与 Agent
  → 幂等记录落库（uk_event 拦重复）
  → 立即 ACK，带 request_id / trace_id / session_id
  → 写 Redis 信箱 → 投 Redis 队列
  → Worker 消费提示 → 抢会话租约（抢不到即让出）
  → 按 tenant + agent + version 读五张表，现场装配 Runtime
  → 调 DeepSeek（真实模型）
  → 逐个消费 Event，工具调用落库
  → 回复经通道主动推送
  → 会话事件、审计、用量落库
  → 释放租约
```

实测：「帮我算 42 乘以 99」→ 会话内三条事件：用户消息、`calculator` 工具调用、`42 × 99 = **4158**`。

### 另外七条

| 链路 | 实测结果 |
|---|---|
| 重复投递 | 同 `event_id` 第二次返回 `duplicate: true`，库中仍 1 行 |
| 多副本租约 | 2 个 Worker 并发 5 条 → 序号 1..10 连续、零冲突 |
| 多租户隔离 | 同名同版本装配出两个独立 Runtime（demo 2 工具/6 策略，acme 1 工具/3 策略） |
| 多后端路由 | acme 会话在 MySQL、demo 在 Redis，同进程并行 |
| 死信隔离 | 毒消息失败→扫描重投→再失败→进死信；期间正常会话 3/3 畅通 |
| 跨进程 trace | 6 span 单根树，跨 gateway 与 worker 两个服务 |
| 灰度回滚 | 权重调整原子生效，三层校验拒绝非法输入 |

**已知缺口：企业微信的长连接模式未实现。**

企业微信提供两种接入方式，二者是方向相反的集成模型：

| | 谁发起连接 | 需公网地址 | 平台侧配置 | 状态 |
|---|---|---|---|---|
| URL 回调 | 平台 → 平台服务 | 需要 | 回调 URL + Token + EncodingAESKey | ✅ 已实现 |
| 长连接 | 平台服务 → 平台 | **不需要** | Bot ID + Secret | ❌ 未实现 |

`Channel` 接口内嵌了 openclaw 的 `Run(ctx) error`，当初就是为长连接留的位置（Mock 通道的注释里写明「A Telegram channel would poll here」）。**但目前没有任何地方调用 `Run()`，它是死代码。** 这与「配置项存在却不生效」是同一类问题：接口看起来支持，实际不支持。

补上它的价值不止多一种选项：长连接不需要公网地址，联调真实企业微信时不必架内网穿透。

## 七、未完成项与优先级

按「缺失会被追问的程度」排序。

### 1. 企业微信长连接，以及让 `Run()` 不再是死代码

不只是补一种模式。接口里存在一个无人调用的方法，与「配置项形同虚设」同类。且长连接无需公网地址，补完即可联调真实企业微信。

做法分两步：先让 Gateway 为 `inbound_mode: stream` 的绑定启动 `Channel.Run(ctx)`，消息汇入**同一条**入站流水线（幂等 → 信箱 → 队列），而不是开一条平行路径；再填企业微信的具体协议实现。

第一步可用一个 stream 模式的 Mock 通道独立验证，不依赖企业微信。

### 2. Memory 与 Summary 至少接通一路

「六类数据统一抽象」目前只有 Session 一路，四个 `DataType` 常量零使用，而这是验收标准第 2 条的核心。框架的 `memory/redis` 子模块现成。

### 3. 危险工具二次确认补上审批通道

表与状态机已就绪，缺 Admin 端点与放行逻辑。

### 4. 压测取容量数据

README 明确要求每节点并发 session 数、平均 token 消耗、Redis / SQL QPS。埋点已全部就绪。

### 5. 其余

| 项 | 说明 |
|---|---|
| `backend_configs` / `backend_bindings` 两表 | 后端映射改为读表而非配置文件 |
| 模型重试、熔断、备用模型 | 韧性缺口 |
| 操作幂等键 | 有副作用工具的重复执行防护 |
| Compose 验证 | 需要一台有 Docker 的机器 |
| 图片与文件消息 | 类型已定义，未实际处理 |
