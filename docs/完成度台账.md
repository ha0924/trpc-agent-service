## 四、已跑通的链路

### 主链路

```text
发消息（curl 或控制台）
  → Gateway 按 webhook_path 查库确定租户与 Agent
  → 幂等记录落库（uk_event 拦重复）
  → 立即 ACK，带 request_id / trace_id / session_id
  → 写 Redis 信箱 → 投 Redis 队列
  → Worker 消费提示 → 抢会话租约（抢不到即让出）
  → 按 tenant + agent + version 读五张表，现场装配 Runtime
  → 调 DeepSeek（真实模型）
  → 逐个消费 Event，工具调用落库
  → 回复经通道主动推送
  → 会话事件、审计、用量落库
  → 释放租约
```

实测：「帮我算 42 乘以 99」→ 会话内三条事件：用户消息、`calculator` 工具调用、`42 × 99 = **4158**`。

### 另外七条

| 链路 | 实测结果 |
|---|---|
| 重复投递 | 同 `event_id` 第二次返回 `duplicate: true`，库中仍 1 行 |
| 多副本租约 | 2 个 Worker 并发 5 条 → 序号 1..10 连续、零冲突 |
| 多租户隔离 | 同名同版本装配出两个独立 Runtime（demo 2 工具/6 策略，acme 1 工具/3 策略） |
| 多后端路由 | acme 会话在 MySQL、demo 在 Redis，同进程并行 |
| 死信隔离 | 毒消息失败→扫描重投→再失败→进死信；期间正常会话 3/3 畅通 |
| 跨进程 trace | 6 span 单根树，跨 gateway 与 worker 两个服务 |
| 灰度回滚 | 权重调整原子生效，三层校验拒绝非法输入 |

**长连接模式已落地。** 企业微信为智能机器人提供两种方向相反的接入方式，现均已实现：

| | 谁发起连接 | 需公网地址 | 平台侧配置 | 状态 |
|---|---|---|---|---|
| URL 回调 | 平台 → 平台服务 | 需要 | 回调 URL + Token + EncodingAESKey | ✅ |
| 长连接 | 平台服务 → 平台 | **不需要** | Bot ID + Secret | ✅ |

`Channel.Run()` 不再是死代码：`gateway.StreamSupervisor` 为 `inbound_mode=stream` 的绑定调度它，消息汇入与回调**同一条**入站流水线（`Gateway.Accept`），幂等与顺序保证仍只有一份实现。

落地时解决的两个结构性问题：

1. **回复路径反转** —— 长连接的回复只能从持有 WebSocket 的 Gateway 进程发出，而两进程不互调 RPC。经 Redis 出站信箱回传：Worker 投递，持连 Gateway 消费并发出。方向相反但机制与正向对称，无实例选择、无阻塞等待。
2. **单连接约束** —— 协议规定同一 bot 只允许一条有效连接、新连接踢掉旧连接。多副本 Gateway 用 per-bot 连接租约选主，复用 Session 租约同一原语。

**仍缺的部分**（诚实记录，勿当已完成）：

| 项 | 说明 |
|---|---|
| 事件回调不入队 | 进入会话与模板卡片事件要求 5 秒内响应，远短于一次 Agent 执行。目前识别并记录后不作答，而非假装支持 |
| 多媒体资源未解密 | 长连接的 `aeskey` 逐 URL 下发（与回调模式的统一 `EncodingAESKey` 不同），字段已解析，解密与下载未实现 |
| 上传临时素材未实现 | 分片上传三步（init / chunk / finish）未实现，因此回复不能带文件与图片 |
| 绑定变更需重启 | stream 绑定在启动时读取一次，新增绑定需重启 Gateway；回调绑定仍无需重启 |
| 群聊未实测 | 单聊已通，群聊（`chatid` 场景）代码路径存在但未对真实群验证 |

**已对真实机器人联调**（2026-09-06）。收发双向均通：真实消息入站解码正确，回复经同一连接发出并被平台接受。四项文档只用文字描述的字段形态已实测定形，记入 `IM通道接入设计.md` §9.2.1：

```text
text="hi"  user="T31560051A"（加密 userid，非明文）
scope="single"  scope_key="T31560051A"（单聊不返回 chatid）
event_id="dd48d208ffdb5a6fdf0883ac82846fff"（明文可读，直接作幂等键）
correlation="7PtkttaERASl-Ec3AMD1ygAA"（回复透传被接受）
```

同时验证了两处设计判断：`stream` + `finish=true` 一次发完的退化用法被真实端点接受（本平台不交付流式）；取消后 `Run()` 正常返回，即 §八 #9 的死锁修复在真实连接上成立。

| 11 | `Redeliver` 丢掉幂等键与关联令牌 | 签名只收 id 与回复文本，从 session 重建入站消息，静默丢掉 `ExternalEventID`（投递状态机的键）与 `CorrelationID`（平台关联令牌）。前者致持连副本无法记录结果，后者致回复退化为主动推送 | 测试 `TestRedelivererContractCarriesOriginalMessage` |

其中第 3、4、7 项同属一类：**看起来已经做了**。已脱敏的假象、已保护的假象、有指标的假象——配置项或方法存在却不生效，比彻底没有更危险，因为它会让人停止追问。

第 9 项是另一类：**只在非主干路径上死锁**。正常关闭走的是外层 ctx 取消，一切正常；只有被新连接踢掉这条路径会挂住，而那恰恰是多副本部署下的常态。它被一个针对协议行为写的测试逮到，不是被压测或人工验证逮到——这也是为什么协议实现值得逐条写测试，而不只是「跑起来看看」。

第 10、11 项又是一类,而且更隐蔽:**把异步交接误当同步完成**。回调模式下 `deliver` 返回即已送达,这个等价关系成立了整整十六个提交;长连接把它打破了——返回只表示交接完成。原代码沿用旧假设,于是「回复丢了但状态是成功」。

这两项是**加长连接时才出现的回归,不是长连接自身的 bug**:改的是既有的投递状态机与重投路径,而它们此前只服务过一种投递语义。教训是引入第二种语义时,凡是隐含「返回即完成」的地方都得重新过一遍——`deliver` 的签名从 `error` 改为 `(queued bool, err error)`,就是把这个区别抬到类型层面,让下一个人无法忽略。
