# 租户隔离机制设计

## 1. 设计目标

平台中的多个租户共享 Gateway、Agent Worker 和存储服务。

为了避免不同租户之间的数据和资源发生混用，平台需要在整个业务链路中携带 `tenant_id` 等隔离 ID，并根据这些 ID 区分租户资源。

当前阶段只确定整体原则，具体的数据结构和实现方式将在后续开发中完善。

## 2. 基本思路

```text
外部请求
→ Gateway 识别租户
→ 构造租户上下文
→ 调度 Agent Worker
→ 执行 Agent
→ 访问配置、数据、工具和密钥
```

Gateway 首先根据可信的用户身份或通道绑定关系确定 `tenant_id`。

之后，`tenant_id` 等隔离 ID 将贯穿整个 Agent 执行链路。各模块在处理请求和访问资源时，都必须使用对应的隔离 ID。

## 3. Worker 与共享存储

Agent Worker 可以同时处理不同租户的请求，并尽量保持无状态。

Worker 中加载的 Agent Runtime 必须包含 `tenant_id`，避免不同租户使用相同 Agent 名称或版本时发生混用。

Session、Memory 等业务状态保存在共享存储中，不与某个 Worker 绑定。不同 Worker 可以根据租户和 Session 信息读取相同的会话状态。

## 4. 主要隔离范围

### 4.1 配置隔离

租户的 Agent、模型、通道和后端配置都需要携带 `tenant_id`。Worker 加载配置时，只能加载当前租户所属的配置。

### 4.2 数据隔离

Session、Memory、Knowledge 和 Artifact 等数据需要携带租户隔离信息。所有数据访问都必须限定在当前租户范围内。

Storage Router 根据租户的 Backend Binding 选择对应的数据后端。

### 4.3 工具权限隔离

Agent 调用工具前，需要根据租户、Agent、用户和运行环境检查工具权限。

工具在访问业务数据时，也必须携带租户隔离信息，避免访问其他租户的数据。

### 4.4 日志隔离与脱敏

日志和审计记录需要携带 `tenant_id`，方便按租户查询和审计。

日志中的密钥、Token、用户隐私和其他敏感信息需要进行脱敏，不能直接记录明文。

### 4.5 密钥隔离

配置中只保存密钥引用，不直接保存密钥内容。

Worker 根据当前租户和 Agent 的配置，在运行时获取所需密钥。不同租户的密钥不能相互访问或混用。

## 5. 当前设计原则

1. Gateway 从可信身份或通道绑定关系确定 `tenant_id`；
2. Gateway 构造租户上下文，并将其传递到整个 Agent 执行链路；
3. Worker 可以共享，但 Agent Runtime 必须包含 `tenant_id`；
4. Session、Memory 等状态保存在共享存储中，不绑定 Worker；
5. 所有数据访问都必须携带租户隔离信息；
6. Storage Router 根据租户配置选择数据后端；
7. 工具执行前需要检查租户和 Agent 的工具权限；
8. 工具内部访问业务数据时，也需要按租户进行过滤；
9. 日志携带租户标识，并对敏感信息进行脱敏；
10. 配置只保存密钥引用，密钥在运行时按租户获取；
11. 具体数据结构、接口和存储方式在后续开发中继续完善。

## 6. 总结

租户隔离的核心是：

> Gateway 确认请求所属租户，后续所有业务逻辑携带相应的隔离 ID。配置、数据、工具、日志和密钥都根据这些隔离 ID 区分租户。

平台的 Worker 由多个租户共享，并尽量保持无状态；需要持久化的 Session、Memory 等业务状态统一保存在共享存储中。
