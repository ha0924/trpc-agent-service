# 多租户机制——租户模型设计

## 1. 设计目标

租户模型用于描述：

- 一个租户拥有哪些 Agent 和平台资源；
- Agent、版本、发布记录及其他配置如何关联；
- 平台如何通过 `tenant_id` 确定资源归属。

当前阶段先确定主要数据表和关联关系。具体字段可以在对应功能和执行链路设计时继续补充。

## 2. 整体模型

```text
Tenant
├── Agent App
│   ├── Agent Version
│   └── Agent Deployment
├── Model Config
├── Tool Definition / Permission
├── Knowledge Base
├── Channel Binding
├── Backend Config / Binding
├── Audit Policy
└── Secret Reference
```

`Tenant` 是所有资源的归属和隔离边界。

## 3. Tenant

Tenant 表示平台中的一个企业、部门或业务团队。

主要保存：

- `tenant_id`
- 租户名称
- 租户状态
- 创建时间
- 更新时间

Agent、模型、工具、知识库、通道和后端配置等资源都必须明确属于某个租户。

## 4. Agent App

Agent App 表示一个独立的 Agent 应用，例如：

- 客服 Agent
- 运维 Agent
- 数据分析 Agent

它主要保存 Agent 的基本信息，不保存具体版本的运行配置。

```text
租户 A
├── 客服 Agent
├── 运维 Agent
└── 数据分析 Agent
```

## 5. Agent Version

Agent Version 表示 Agent 的一个具体配置版本。

一个版本可以包含：

- Agent 类型和编排方式；
- Prompt；
- 模型配置；
- 工具权限；
- 知识库配置；
- Memory 配置；
- Plugin / Guardrail 配置。

例如：

```text
客服 Agent
├── v1：旧 Prompt 和旧工具
├── v2：新 Prompt 和新工具
└── v3：测试版本
```

已经发布的版本原则上不直接修改。配置变化时创建新版本，方便追踪、灰度和回滚。

## 6. Agent Deployment

Agent Deployment 表示 Agent 当前的发布状态。

例如：

```text
客服 Agent
├── v1：历史版本
├── v2：生产环境当前版本
└── v3：测试环境当前版本
```

第一版可以记录：

```text
Agent + 环境 → 当前发布版本
```

以后支持灰度时，可以记录：

```text
生产环境
├── v2：90% 流量
└── v3：10% 流量
```

因此：

- Agent Version 说明“配置是什么”；
- Agent Deployment 说明“当前发布哪个版本”。

## 7. Model Config

Model Config 保存租户可以使用的模型配置，例如：

- 模型供应商；
- 模型名称；
- API 地址；
- 默认生成参数；
- 超时和重试配置；
- API Key 的密钥引用。

Agent Version 可以引用一个 Model Config。

## 8. Tool Definition 与 Permission

Tool Definition 定义租户可以使用的工具，例如：

- 查询订单；
- 创建工单；
- 调用内部 API；
- MCP 工具。

Tool Permission 定义某个 Agent Version 对工具的权限：

```text
allow：允许调用
deny：禁止调用
ask：调用前需要确认
```

工具本身和 Agent 分开保存，通过关联表完成绑定。

## 9. Knowledge Base

Knowledge Base 表示租户的知识库，例如：

- 产品文档库；
- 客服问答库；
- 公司制度库。

一个 Agent Version 可以绑定多个知识库，一个知识库也可以被多个 Agent Version 使用。

具体文档、切片和向量索引可以存放在租户配置的知识库存储后端。

## 10. Channel Binding

Channel Binding 表示外部消息通道与 Agent 的绑定关系，例如：

```text
企业微信应用
→ 租户 A
→ 客服 Agent
→ 生产环境 Deployment
→ 最终选择 Agent Version
```

Channel Binding 默认关联 Agent Deployment，由 Deployment 决定当前使用哪个版本。

同时可以保留固定版本能力，用于：

- 测试指定版本；
- 内部调试；
- 特定通道固定使用某个版本。

因此可以理解为：

```text
普通通道 → Deployment → 当前发布版本
测试通道 → 固定 Agent Version
```

## 11. Backend Config 与 Backend Binding

Backend Config 定义一个可使用的数据后端，例如：

- Redis；
- MySQL；
- PostgreSQL；
- Qdrant；
- Milvus；
- S3。

Backend Binding 表示某个 Agent 使用哪个后端：

```text
客服 Agent
├── Session → Redis
├── Memory → PostgreSQL
├── Knowledge → Qdrant
├── Artifact → S3
└── Audit Log → ClickHouse
```

Backend Binding 主要和 Agent 关联，必要时允许 Agent Version 覆盖默认配置。

`tenant_id` 仍然需要保留，用于校验这些后端资源属于哪个租户。

## 12. Audit Policy

Audit Policy 表示 Agent 执行时采用的审计规则，例如：

- 是否记录模型调用；
- 是否记录工具调用；
- 是否记录消息正文；
- 是否进行敏感信息脱敏；
- 审计记录保存多久；
- 危险操作是否需要审批。

审计策略的具体字段需要结合 tRPC-Agent-Go 的执行链路，以及 Plugin、Callbacks、Event Hook 的实现进一步设计。

当前阶段只确定：

- 审计策略属于某个租户；
- 审计策略可以绑定 Agent 或 Agent Version；
- Agent 执行时加载对应策略；
- 具体策略内容保留扩展能力。

## 13. Secret Reference

Secret Reference 保存密钥在密钥存储中的引用，不直接保存明文。

例如：

- 模型 API Key；
- 企业微信 Secret；
- 数据库密码；
- MCP Token；
- 第三方服务凭据。

配置表中只保存类似以下引用：

```text
secret://tenant-a/model/deepseek-key
```

Worker 加载 Agent Runtime 时获取密钥，并只在内存中使用。

## 14. 第一版主要数据表

```text
tenants

agent_apps
agent_versions
agent_deployments
deployment_versions

model_configs

tool_definitions
agent_version_tools

knowledge_bases
agent_version_knowledge_bases

channel_bindings

backend_configs
backend_bindings

audit_policies

secret_references
```

## 15. 核心关联关系

```text
Tenant
  └── Agent App
        ├── Agent Version
        │     ├── Model Config
        │     ├── Tool Permission
        │     ├── Knowledge Base
        │     ├── Backend Binding
        │     └── Audit Policy
        │
        └── Agent Deployment
              ├── 当前发布版本
              └── Channel Binding
```

## 16. 当前设计原则

1. `Tenant` 是资源归属和隔离边界；
2. Agent 使用 App、Version、Deployment 三层模型；
3. Version 保存配置，Deployment 保存发布状态；
4. Channel 默认绑定 Deployment，也可以固定到指定 Version；
5. Backend Binding 主要与 Agent 关联，Version 可以覆盖；
6. 工具和知识库通过关联表绑定 Agent Version；
7. 密钥只保存引用，不保存明文；
8. 当前先确定表和关系，具体字段结合后续执行链路继续设计。
