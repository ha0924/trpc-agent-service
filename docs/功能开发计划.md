清单与状态见 [功能清单.md](功能清单.md)，完成度见 [完成度台账.md](完成度台账.md)。

## 二、开发顺序

排序依据是**风险**，不是重要性。风险的定义：

1. 是否改动已有抽象 —— 改了就可能带出回归，本项目已有两次前例（台账 §八 #10 #11）；
2. 是否依赖外部系统 —— 依赖了就可能卡住；
3. 是否有现成模式可循 —— 有就快且稳。

### 第一批：纯增量，不碰任何已有代码路径（7 项）

| 序 | 项 | 内容 |
|---|---|---|
| 1.1 | A2 | 租户 创建/更新/停用 |
| 1.2 | A3 | Agent App 创建/更新/下线 |
| 1.3 | A4 | Agent 版本 创建/发布/归档 |
| 1.4 | A6 | 工具权限 配置接口 |
| 1.5 | A8 | IM 通道绑定 配置接口 |
| 1.6 | A11 | 上述端点汇入 Admin API |
| 1.7 | A1 | 租户模型第 7 要素（审计策略）随 A2 一并落表 |

**为何排第一**：消掉的是任务描述**第一句**——「平台需要支持多个租户创建和部署自己的 Agent」。目前「部署」有了（灰度权重可改），「创建」全部只能手写 SQL。

**为何风险最低**：纯新增端点，不修改任何现有读路径。`store` 层已有完整的读 SQL 与事务模式可同构套用，`admin` 包已有路由与错误处理骨架。写坏了也只影响新端点。

**验收**：能只用 HTTP 接口走完「建租户 → 建 Agent → 建版本 → 发布 → 绑通道 → 发消息拿到回复」，全程不碰 SQL。

---

### 第二批：接通已存在但未接线的代码（3 项）

| 序 | 项 | 内容 |
|---|---|---|
| 2.1 | F5 | 危险工具审批：接上 `tool_approvals` 状态机 + 放行端点 |
| 2.2 | C8 | MCP 工具挂载 |
| 2.3 | C9 | Skill 挂载 |

**为何排第二**：这三项是「看起来做了」的假象——表、DDL、函数、绑定表读取全都在，唯独没接上。这类缺口比彻底没做更危险，因为一应俱全会让人停止追问。F5 更是本项目**第四次**栽在「函数存在、零调用点」上。

**为何风险低**：F5 的放行端点与第一批同批做，顺路完成；C8/C9 是在装配流程里增加挂载分支，装配已按列表遍历，加一类不改结构。

**验收**：F5 —— 危险工具被拦后能在 Admin 查到待审请求，批准后重发消息即放行；C8/C9 —— 绑定表里配了就真的挂上，日志不再是 `present but not yet mounted`。

---

### 第三批：新增数据类别，流经已有路由（4 项）

| 序 | 项 | 内容 |
|---|---|---|
| 3.1 | D3 | Memory 存储接通一路 |
| 3.2 | D8 | 六类数据统一抽象：让 `DataType` 常量真的被使用 |
| 3.3 | D4 | Summary 存储 |
| 3.4 | D10 | event/state/summary 更新顺序补齐 summary |

**为何排第三**：这是**验收标准第 2 条**的核心。多后端路由是真的，但流经它的数据只有 Session 一类，四个 `DataType` 常量使用点为 0。接通 Memory 一路能同时消掉 D3 + D8 + D11。

**为何风险中等**：要在 Runtime 装配时注入新的存储服务，即**改动装配流程**——比第一二批多一层。但 Storage Router 的路由逻辑已定型，新数据类别走同一套 `Resolve`，不改路由本身。

**验收**：两个租户的 Memory 分别落在不同后端，跨 Worker 可见；同一会话的 summary 在 event 之后更新，顺序可查。

---

### 第四批：改动已有抽象（6 项）

| 序 | 项 | 内容 |
|---|---|---|
| 4.1 | — | 拆分入站/出站模式两个维度（E0 的前置） |
| 4.2 | E0/E5 | Telegram 通道 |
| 4.3 | E20 | 图片/文件消息 |
| 4.4 | I5 | 操作幂等键 |
| 4.5 | I4 | 模型重试、备用模型、熔断 |
| 4.6 | J1 | 容量评估 |

**为何排最后**：这批都要动已有代码路径。

4.1 是发现的一处设计债：`InboundMode` 现在同时承载「入站怎么进来」和「出站怎么出去」两件事。企业微信长连接下二者恰好一致（回复必须走原 socket），但 Telegram 的 long polling 是「入站主动拉取、出站独立 HTTPS」——任何 Worker 都能回。若直接标 `stream` 会被错误路由到出站信箱，绕远路还引入不必要的 per-bot 选主。

**这一步必须单独一个提交，不与新通道混做**——否则出问题时分不清是新通道的 bug 还是抽象改动的 bug。这个教训来自 §八 #10 #11：那两个静默丢回复的缺陷，正是「加新东西时改坏了旧假设」。

4.4/4.5 触及工具执行与模型调用的主路径，风险最高，放最后。I5 尤其值得做：设计文档反复强调「有副作用的 Tool 不能重复执行」，风险清单 #2 也列了，但**防护本身没实现**——这是文档与代码的一处实质不符。

4.6 容量评估放最后，因为压测数字的说服力取决于被压系统的完整度。前三批做完再压，数字才有意义；否则补完功能还得重压一遍。

**验收**：4.2 —— Telegram 真实收发，且回调模式绑定不受影响；4.6 —— 给出每节点并发 session 数、平均 token 消耗、Redis/SQL QPS，以及瓶颈定位与扩容依据。

## 三、每批的收口动作

每批结束都要做完这四件，不留尾巴：

1. **测试** —— 隔离性与顺序性必须有用例（CLAUDE.md 硬要求）；
2. **文档同步** —— 改了行为就改设计文档，发现坑就回写；台账与功能清单的状态同步更新；
3. **`format.sh` / `lint.sh` / `go test ./...`** 全过；
4. **提交并推送**，提交信息写清「为什么这么做」而非「做了什么」。

## 四、预期结果

四批做完，未完成项从 43 降到 23，且剩下的 23 项全部是**主动裁剪**而非遗漏——每一项都有不做的理由写在 §一。

按功能清单的口径，完成度从 83 ✅ / 15 ⚠️ / 28 ❌ 变为约 103 ✅ / 3 ⚠️ / 20 ❌。

更重要的是性质变化：

| | 现在 | 四批后 |
|---|---|---|
| README 字面要求 | 6 项未满足 | 0 |
| 验收标准点名 | 4 项未满足 | 0 |
| 「看起来做了」的假象 | 3 项 | 0 |
| 韧性缺口 | 2 项 | 0 |

「假象」归零是这份计划里最该被看重的一项。它不增加功能数量，但它决定了这份交付里**哪些结论可以被信任**。
