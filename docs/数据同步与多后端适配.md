# 数据同步与多后端支持设计

## 1. 设计目标

平台需要支持不同租户、不同 Agent App 根据数据用途选择不同的存储后端，并保证多个 Agent Worker 访问共享数据时具备必要的一致性、可见性和幂等性。

tRPC-Agent-Go 已经提供 Session、Memory、Knowledge、Artifact 及其多种后端实现。平台层主要负责保存后端配置和绑定关系，并在构建 Agent Runtime 时选择对应的框架实现。

当前阶段先确定整体方案，具体接口、字段和存储实现将在后续开发中完善。

## 2. 多后端选择与路由

不同数据类型需要分别选择后端，而不是为一个 Agent App 设置单一的存储后端。

例如：

```text
租户 A / 客服 Agent
├── Session、Summary → Redis
├── Memory           → PostgreSQL
├── Knowledge        → Qdrant
├── Artifact         → S3
└── Audit Log        → MySQL
```

平台通过两类配置管理后端：

- `Backend Config`：记录 Redis、MySQL、PostgreSQL、Qdrant、S3 等后端的连接配置；
- `Backend Binding`：记录 Agent App 的某类数据使用哪个 Backend Config。

Worker 收到请求后，根据以下信息选择后端：

```text
tenant_id + agent_app_id + 数据类型
```

选择后端后，再根据 `user_id`、`session_id` 等业务 ID 访问具体数据。

整体路由过程如下：

```text
Worker 收到请求
→ 根据 tenant_id、agent_app_id 和数据类型查找 Backend Binding
→ 获取对应的 Backend Config
→ 创建或复用对应的框架 Service
→ 根据 user_id、session_id 等业务 ID 读写数据
```

Worker 可以缓存已经创建的 Service 和连接，但后端配置和业务数据不能依赖某个 Worker。Worker 重启后，应能够从配置中心重新构建所需的存储服务。

## 3. 统一数据访问抽象

业务模块只访问 Session、Memory、Knowledge、Artifact 等数据能力，不直接依赖 Redis、MySQL 或其他具体后端。

平台通过 Storage Router 和 tRPC-Agent-Go 已有的数据接口完成后端适配。

| 数据类型 | 主要内容 | 建议后端 |
| --- | --- | --- |
| Session | 会话基本信息和会话状态 | Redis、MySQL、PostgreSQL、SQLite、MongoDB 等 |
| Event | 用户消息、Agent 回复、工具调用等事件 | 跟随 Session 后端 |
| Summary | Session 历史内容的摘要 | 跟随 Session 后端 |
| Memory | 用户或 Agent 的跨会话长期记忆 | Redis、MySQL、PostgreSQL、外部 Memory 服务等 |
| Knowledge | 文档切片、Embedding 和检索索引 | Qdrant、Milvus、pgvector 等向量存储 |
| Artifact | 图片、文件、音视频等产物 | S3、COS 等对象存储 |
| Audit Log | 模型调用、工具调用、权限判断和异常记录 | MySQL、PostgreSQL、ClickHouse 或日志系统 |

其中，Summary 是 Session Service 的一部分，一般跟随 Session 后端，不需要单独选择存储。

## 4. 数据同步策略

### 4.1 多节点并发写入同一 Session

通过 Session Scheduler 对同一个 Session 的请求进行顺序处理，避免多个 Worker 同时修改同一份 Session 数据。

Session 保存在共享后端中，不与某个 Worker 绑定，因此后续请求可以由不同 Worker 继续处理。

### 4.2 Event、State 和 Summary 的更新顺序

Worker 执行 Agent 后，先持久化 Event，再更新对应的 Session State。Event 和 State 应尽量通过事务或原子操作保持一致。

Event 和 State 保存成功后，再异步生成 Summary。Summary 更新失败可以重试，不影响当前会话继续执行。

```text
Agent 执行
→ 保存 Event
→ 更新 Session State
→ 提交 Summary 任务
→ 异步生成并保存 Summary
```

### 4.3 Memory 写入后的跨节点可见性

Memory 保存在 Redis、SQL 或外部 Memory 服务等共享后端中。所有 Worker 根据相同的后端绑定访问共享 Memory，因此一个 Worker 写入后，其他 Worker 可以重新读取最新数据。

Worker 不保存 Memory 的唯一副本。如果后续增加本地缓存，需要设置合理的过期或刷新机制。

### 4.4 后端数据迁移

当 Session、Memory 或 Knowledge 更换后端时，采用以下迁移流程：

```text
创建并初始化新后端
→ 全量复制历史数据
→ 同步迁移期间产生的增量数据
→ 校验新旧后端数据
→ 切换 Backend Binding
→ 观察运行状态
→ 保留旧后端用于短期回滚
```

迁移期间继续由旧后端提供服务，通过增量同步保持新后端数据更新，从而尽量避免停机。

普通数据迁移到向量数据库时，需要在迁移过程中增加文档切片和 Embedding 向量化处理，但整体迁移流程不变。

### 4.5 IM 消息重复投递

平台使用租户、通道账号和 IM 消息 ID 组成幂等键：

```text
tenant_id + channel_type + channel_account_id + message_id
```

幂等记录保存在共享存储中，并通过原子操作完成检查和首次占位。首次收到的消息正常执行，重复消息不再重复调用 Agent 或工具。

消息乱序、回复重试和频率限制等问题，在 IM 软件接入模块中进一步设计。

## 5. 不同后端的选择与取舍

- **InMemory**：读写速度快，但不能跨 Worker 共享，适合本地开发和测试；
- **Redis**：读写延迟低，适合 Session、临时状态和消息幂等记录；
- **MySQL / PostgreSQL**：支持事务，数据可靠，适合 Event、State、Memory、配置和审计数据；
- **MongoDB**：数据结构灵活，适合 Session、Event 等文档型数据；
- **向量库**：适合 Knowledge 和向量化 Memory，索引更新可以接受短暂延迟；
- **对象存储**：适合图片、文件等 Artifact，存储成本较低，但不适合频繁更新的结构化数据；
- **外部 Memory 服务**：适合长期记忆，其一致性和访问延迟由外部服务决定。

总体原则如下：

- Session、State 和幂等记录更重视一致性和及时可见；
- Summary、Memory 和 Knowledge 可以根据业务接受一定的同步延迟；
- Artifact 更重视持久保存和存储成本；
- Audit Log 更重视记录完整和可追踪。

## 6. 最小数据模型

本节主要补充 Agent 运行过程中产生的数据。Tenant、Agent Version、Agent Deployment、Backend Config 等控制面模型沿用《多租户机制——租户模型设计》。

整体关系如下：

```text
Tenant
  └── Agent App
      ├── Session
      │   ├── Event
      │   └── Summary
      ├── Memory
      ├── Channel Binding
      └── Audit Log
```

### 6.1 Tenant

表示资源所属的租户。

```text
tenants
- tenant_id
- tenant_name
- status
- created_at
- updated_at
```

### 6.2 Agent App

表示租户下的一个 Agent 应用。

```text
agent_apps
- agent_app_id
- tenant_id
- agent_name
- description
- status
- created_at
- updated_at
```

### 6.3 Session

表示用户与某个 Agent App 的一次会话，并保存当前会话状态。

```text
sessions
- session_id
- tenant_id
- agent_app_id
- agent_version
- user_id
- state
- status
- created_at
- updated_at
```

### 6.4 Message / Event

记录 Session 中发生的用户消息、Agent 回复、工具调用和工具结果等事件。

```text
session_events
- event_id
- tenant_id
- agent_app_id
- session_id
- request_id
- event_type
- role
- content
- sequence
- created_at
```

`sequence` 用于表示 Event 在 Session 中的顺序。

### 6.5 Memory

记录用户或 Agent App 的跨会话长期记忆。

```text
memories
- memory_id
- tenant_id
- agent_app_id
- user_id
- content
- metadata
- created_at
- updated_at
```

### 6.6 Summary

记录某个 Session 的历史摘要。

```text
session_summaries
- summary_id
- tenant_id
- agent_app_id
- session_id
- summary
- covered_event_sequence
- created_at
- updated_at
```

`covered_event_sequence` 表示当前 Summary 已经覆盖到哪个 Event，用于后续增量更新。

### 6.7 Channel Binding

记录外部 IM 通道账号与 Agent App 或 Agent Deployment 的绑定关系。

```text
channel_bindings
- channel_binding_id
- tenant_id
- agent_app_id
- deployment_id
- channel_type
- channel_account_id
- status
- created_at
- updated_at
```

### 6.8 Audit Log

记录 Agent 执行过程中的关键操作。

```text
audit_logs
- audit_id
- tenant_id
- agent_app_id
- session_id
- request_id
- trace_id
- user_id
- channel_type
- event_type
- tool_name
- decision
- latency
- error_type
- cost
- created_at
```

以上表结构只用于表达最小数据关系。具体字段类型、索引、外键、分区和不同后端的实际结构，将在后续实现阶段完善。

## 7. 总结

平台不为 Agent App 设置单一的存储后端，而是分别为 Session、Memory、Knowledge、Artifact 和 Audit Log 绑定合适的后端。

Worker 根据 `tenant_id`、`agent_app_id` 和数据类型完成后端选择，再根据 `user_id`、`session_id` 等业务 ID 访问具体数据。多个 Worker 通过共享存储实现数据共享，并通过 Session 顺序调度、原子写入、异步 Summary、消息幂等和可回滚的数据迁移保证基本的数据一致性。
