## 四、三个核心设计决策

### 两进程 + 队列，而非单进程

企业微信的被动响应窗口是秒级，而一次 Agent 执行常达数十秒。硬扛必然超时，因此入站与执行必须解耦：

```text
Gateway  收消息 → 幂等落库 → ACK → 写信箱 → 投队列
Worker   消费提示 → 抢租约 → 排空信箱 → 执行 → 主动推送
```

两者**不互相调用**，只通过队列与共享存储协作。Gateway 不做服务发现、不维护 Worker 列表、不选择由谁执行——由消费者争抢。因此 Worker 的增减对 Gateway 完全透明。

入站三步顺序是固定的：**幂等落库 → ACK → 入队**。先落库使在途请求始终有可靠记录；先 ACK 使平台停止重投；后入队使队列失败只造成延迟而非丢消息。

### 顺序由租约保证，不依赖队列

同一会话的顺序不靠队列的顺序特性，而靠 Redis 上的租约与信箱：

```text
租约  同一时刻只有一个 Worker 能处理某会话，带 TTL 自动过期
信箱  该会话待处理的消息，按到达顺序排列
```

租约**按轮持有**——抢到、排空信箱、释放——因此下一轮可落到任意健康 Worker。这就是「Worker 可互换、不需要 sticky session」的实现方式，而 TTL 同时就是故障恢复时间上限。

由此队列的契约被压到最薄：at-least-once、不要求有序、不要求可靠。契约越弱可替换性越强。

### Runtime 配置驱动装配

`trpcservice/agent` 包**不含任何 Agent 定义**。提示词、模型、Tool、扩展、MCP、Skill 全部来自数据库，按 `tenant + agent + version` 在请求时装配并缓存。

这是「多租户」真伪的分界线：写死在代码里的 Agent，是单租户服务套了个多租户的表结构。

## 五、实测结论

### 真实模型链路

```text
model_note=live
回复："我是一个乐于助人的助手，会简洁准确地回答你的问题，不确定时会坦诚说明。"
```

回复**遵守了数据库里配置的提示词**，证明配置驱动装配确实生效。

用量真实记录：734 prompt + 18 completion tokens，$0.000108，858ms。

工具调用链路完整：`帮我算 9876 除以 4` → 调用 calculator → `9876 ÷ 4 = **2469**`。

### 多租户隔离（对抗性验证）

第二个租户**刻意**使用与第一个完全相同的 `agent_app_id` 与版本号 `v1`。若 Runtime 缓存键遗漏 `tenant_id`，两者会共用同一个 Runtime，也就共用了模型、工具与密钥。

```text
key=tenant-demo/assistant/v1  tools=2  extensions=6
key=tenant-acme/assistant/v1  tools=1  extensions=3
```

装配出两个独立实例。`tools=1` 同时证明 acme 的 `search: deny` 生效。

会话隔离：两租户都有名为 `alice` 的外部用户，落到两个不同会话。凭据隔离：demo 的通道 token 打 acme 的 webhook 返回 401。

### 跨进程 trace

```text
gateway.inbound                            [gateway]
└─ worker.round                            [worker]    抢到租约的一轮
   └─ worker.message                       [worker]    单条消息
      ├─ worker.deliver                    [worker]    出站投递
      └─ invoke_agent tenant-demo-...-v1   [worker]    框架自动埋点
         └─ chat deepseek-chat             [worker]    模型调用
```

一条消息一棵树，单根、跨两个服务。最后两层由框架产生并自动挂到平台 span 之下——这是复用框架 `telemetry/trace` 而非自建 provider 的收益。

同一个 `trace_id` 可在 trace 树、两个进程的日志、`session_events`、`inbound_events`、`audit_logs` 中相互查找。

### 死信隔离

完整闭环实测：失败 → 对账扫描重投 → 再失败 → 达到上限 → 进死信。

**核心性质**：毒消息反复失败期间，正常会话 3/3 全部正常收到回复。

### 端到端验收

`./scripts/acceptance.sh` — **28 项全部通过**，覆盖入站顺序、验签路由、租户隔离、配置装配、灰度回滚、治理审计、指标、死信、trace 贯穿。
