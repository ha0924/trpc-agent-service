# 故障恢复与运维设计

## 1. 设计目标

平台需要在 Worker、IM 平台、数据库、模型服务或 Tool 服务出现短暂故障时，尽量保证：

- 不重复执行同一条 IM 消息；
- 不重复调用可能产生副作用的 Tool；
- 不因单个 Worker 故障导致某个 Agent 或 Session 永久不可用；
- 已经完成的 Agent 执行可以继续完成 IM 回复；
- 可以安全发布新版本、回滚配置和水平扩容；
- Go 服务在超时、取消或关闭时不会遗留 goroutine 和事件通道泄漏。

第一版重点明确恢复原则、状态边界和部署方式。具体的重试次数、超时参数、消息队列和 SDK 错误码在实施阶段结合实际组件确定。

## 2. 故障恢复基础

当前架构采用以下原则：

```text
Worker 尽量无状态
Session / Memory / Event 保存在共享后端
Session 不绑定某个 Worker
Agent Version 和配置由控制面保存
Worker Runtime 只是本地缓存，可重新构建
```

因此，单个 Worker 故障不会丢失平台配置、Session 或长期 Memory。健康 Worker 可以根据：

```text
tenant_id + agent_app_id + agent_version
```

重新加载 Runtime，并从共享存储恢复上下文。

## 3. 节点故障

### 3.1 Worker 故障

当某个 Agent Worker 宕机、网络不可达或健康检查失败时：

```text
Gateway / Session Scheduler
→ 不再向该 Worker 分派新请求
→ 选择健康 Worker 继续处理新请求
```

后续同一个 Session 的消息可由其他 Worker 处理：

```text
健康 Worker
→ 读取共享 Session / Memory
→ 按当前版本重新构建 Runtime
→ 继续执行
```

同一 Session 的执行权需要支持超时释放或租约机制。否则某个 Worker 持有执行权后异常退出，Session 可能一直被阻塞。

第一版只要求保证：

```text
Worker 故障后不会永久占用 Session；
执行权超时或节点被判定失效后，可以由其他 Worker 接管后续消息。
```

具体使用 Redis 锁、任务队列或数据库状态机，在实施阶段选择。

### 3.2 Gateway、Channel Adapter 故障

Gateway 和 Channel Adapter 都应部署多个实例，并通过负载均衡接收 IM 回调或其他请求。

实例故障时：

```text
负载均衡
→ 将后续回调发送给其他健康实例
```

IM 平台可能重新投递未确认的回调。平台通过入站幂等记录避免重复执行。

## 4. IM 消息重试和幂等

IM 重试需要区分入站和出站两部分。

### 4.1 入站消息重复投递

IM 平台可能因为网络超时或回调确认失败，重复发送同一个事件。

处理流程：

```text
IM 平台提供 event_id / message_id
→ Channel Adapter 提取事件标识
→ Gateway 在共享存储创建幂等记录
→ 首次事件继续执行
→ 已处理或处理中事件不重复执行
```

幂等记录建议包含处理状态：

```text
processing：正在执行
succeeded：执行和投递已完成
delivery_failed：Agent 已完成，但 IM 回复发送失败
failed：执行失败
```

### 4.2 出站 IM 回复失败

Agent 已经生成回复、Session 已经写入后，IM 平台发送接口仍可能失败。

此时不能重新运行 Agent 或 Tool。正确流程是：

```text
Agent 执行完成
→ 保存最终回复或投递记录
→ IM 发送失败
→ 标记 delivery_failed
→ 仅重试 IM 投递
```

这样可以避免重复调用模型、重复写入 Memory，或重复执行创建工单、退款、重启服务等 Tool。

## 5. 共享存储短暂不可用

不同数据的重要性不同，故障时采用不同策略。

| 数据或能力 | 不可用时的处理原则 |
| --- | --- |
| 入站幂等记录、Session 执行权 | 不能确认状态时不继续执行，短暂重试后快速失败，避免重复执行 |
| Session Event、Session State | 无法可靠写入时，不继续执行可能有副作用的后续流程 |
| Memory | 有限重试；必要时本次请求不使用或延后写入长期 Memory |
| Summary | 异步重试，不阻塞当前 IM 回复 |
| Knowledge 检索 | 降级为不使用知识库检索，或提示当前知识库暂不可用 |
| Artifact | 记录待补偿任务，后续重试上传 |
| 普通 Audit / Usage | 可异步缓冲和重试 |
| 高风险审计事件 | 在危险 Tool 执行前可靠记录，记录失败时不执行高风险操作 |

总体原则：

> 对 Session、Event、幂等记录等强依赖状态，状态不确定时宁可失败，也不要重复执行。对 Summary、Knowledge、Artifact 等允许最终一致的数据，可以异步重试或功能降级。

## 6. 模型和 Tool 故障

### 6.1 模型超时或不可用

模型调用应有单次超时和整条请求的总超时。

发生模型超时或短暂错误时：

```text
有限次数重试
→ 可选切换到备用模型
→ 超过总超时后结束请求
→ 返回明确的失败或稍后重试提示
```

模型重试必须受预算和总超时限制，不能无限重试。

### 6.2 Tool 执行失败

Tool 是否可以自动重试，取决于是否有副作用。

```text
查询、读取类 Tool
→ 可在有限次数内重试

创建工单、退款、重启服务、发送通知等副作用 Tool
→ 必须使用 tool_operation_id 或下游 Idempotency-Key
→ 下游确认支持幂等后才允许自动重试
→ 结果不确定时进入人工处理或补偿，不盲目重试
```

Tool 调用失败后，Agent 可以根据 Tool 返回的错误选择：

```text
重试
换一种处理方式
向用户说明当前能力不可用
结束本次请求
```

## 7. Go 运行时资源管理

### 7.1 context.Context

每次请求创建根 `context.Context`，并向下传递给：

```text
Gateway
→ Session Scheduler
→ Worker / Runner
→ LLM Client
→ Tool / MCP Client
→ Storage Adapter
→ IM Outbound Client
```

以下情况应取消 Context：

```text
请求总超时
Session 排队超时
模型或 Tool 调用超时
Worker 优雅停机
系统主动熔断或取消
```

所有下游调用都应尊重 `ctx.Done()`，在取消后尽快结束。

### 7.2 goroutine 生命周期

原则：

- 每个请求创建的 goroutine 必须有明确退出条件；
- 不创建无限等待的后台 goroutine；
- Summary、审计、投递重试等后台工作使用受控 Worker Pool 或任务队列；
- Worker 停机时先停止接收新任务，再等待或取消正在执行的任务；
- 网络调用、Tool 调用和 Channel 写入都必须设置超时。

### 7.3 Runner Event 通道

Runner 可能持续产生流式 Event。消费端必须持续读取：

```text
直到 Event 通道关闭
或 Context 被取消
```

如果消费端提前停止读取，而 Runner 仍在写 Event，可能造成阻塞和 goroutine 泄漏。

Worker 优雅关闭时建议按以下顺序处理：

```text
停止接收新请求
→ 等待当前请求在限定时间内完成
→ 超时后取消 Context
→ 持续消费或排空 Runner Event
→ 关闭 IM、存储和模型 Client
→ Worker 退出
```

## 8. 灰度发布和配置回滚

### 8.1 第一版灰度发布

第一版支持 Agent Version 的权重灰度发布。

```text
客服 Agent / production
├── v1：90%
└── v2：10%
```

Gateway 在创建新 Session 时：

```text
读取当前 Deployment
→ 根据版本权重和稳定标识选择 Agent Version
→ 将 agent_version 写入 Session
```

后续同一 Session 一直使用已经绑定的版本，避免一次对话中突然切换 Prompt、Tool 或行为。

第一版可使用稳定哈希分桶实现权重选择。Gateway 是唯一需要理解灰度策略的组件：

```text
Gateway：选择 Version
Session Scheduler：保证顺序并分派 Worker
Worker：加载指定 Version 的 Runtime 并执行
```

Deployment 需要预留策略扩展字段。第一版实现按权重分流，后续可扩展为指定 Tenant、Channel、用户或标签的灰度规则。

### 8.2 回滚

Agent Version 是不可变配置快照，不直接修改已发布版本。

回滚方式：

```text
调整 Deployment 的版本权重
或将 Deployment 指回上一稳定 Version
```

例如：

```text
v1：90%，v2：10%
→ 发现 v2 异常
→ v1：100%，v2：0%
```

新 Session 会立即使用稳定版本。严重安全问题时，可按运维操作要求强制停止异常版本。

## 9. 容量评估

第一版完成后再通过压测和真实运行指标确定具体容量，不在当前方案中给出固定并发数或 QPS。

需要重点采集和评估：

```text
IM 入站峰值 QPS
Agent 请求平均和 P95 执行时长
单 Worker 并发执行数
Session Scheduler 排队长度和等待时间
模型调用耗时、Token 吞吐和错误率
Tool 调用次数、耗时和失败率
Redis / SQL QPS、连接数、延迟和错误率
IM 出站投递量、成功率和重试量
Worker CPU、内存和 goroutine 数
```

初期采用保守的并发限制和水平扩缩容。获得压测数据后，再确定：

```text
每个 Worker 的资源规格
每个 Worker 的并发上限
Redis / SQL 的容量
自动扩缩容阈值
```

## 10. 部署方案

### 10.1 最小可运行部署

用于本地开发、验证和 Demo，可使用 Docker Compose：

```text
Docker Compose
├── Agent Gateway + Channel Adapter
├── 单个 Agent Worker
├── Redis
├── MySQL 或 PostgreSQL
├── 可选：向量数据库
└── 可选：MinIO 等对象存储
```

最小部署特点：

- 单 Worker；
- 使用测试 IM 通道或本地模拟回调；
- 使用简化的 Secret Provider；
- 基础日志、Metrics 和 Trace；
- 不要求所有组件高可用。

### 10.2 生产推荐部署

生产环境推荐使用 Kubernetes 或等价的容器编排平台：

```text
Kubernetes
├── Gateway / Channel Adapter 多副本
├── Session Scheduler 多副本
├── Agent Worker Deployment
├── Worker HPA 自动扩缩容
├── Redis 高可用
├── MySQL / PostgreSQL 高可用
├── 向量数据库 / 对象存储
├── Admin API / 配置中心
├── Secret Manager
├── OpenTelemetry Collector
└── Metrics、Trace、日志和告警系统
```

生产环境需要具备：

```text
健康检查
滚动发布
资源配额
自动扩缩容
故障告警
数据备份和恢复演练
网络访问控制
密钥访问控制
```

## 11. 第一版范围

第一版重点实现和验证：

1. Worker 无状态、Session 不绑定 Worker；
2. IM 入站幂等和出站投递重试；
3. Session / Event / State 的可靠写入边界；
4. Summary、Knowledge、Memory 等数据的异步重试或降级；
5. 模型和查询类 Tool 的有限重试；
6. 有副作用 Tool 的幂等键和人工补偿原则；
7. Context 取消、goroutine 生命周期和 Runner Event 通道安全关闭；
8. Agent Version 权重灰度发布和 Deployment 回滚；
9. Docker Compose 最小部署与 Kubernetes 生产部署建议；
10. 基于监控和压测进行后续容量评估。
