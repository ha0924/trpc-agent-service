# 一期表结构

一期建表 12 张，覆盖四条链路：识别租户、定位会话、装配 Runtime、数据落库。

全部表清单与用途见 `docs/技术实现文档/数据模型设计.md`，本文只给出一期落地的部分。

## 1. 建表范围

| 表 | 一期作用 |
|---|---|
| `tenants` | 租户上下文的来源 |
| `agent_apps` | 定位 Agent |
| `agent_versions` | Runtime 装配的输入，含 Prompt 与模型配置 |
| `agent_tool_bindings` | 本版本可用哪些 Tool |
| `agent_extension_bindings` | 本版本启用哪些 Plugin、Guardrail、Callback |
| `agent_mcp_bindings` | 本版本使用哪些 MCP 服务 |
| `agent_skill_bindings` | 本版本挂载哪些 Skill |
| `agent_deployments` | 决定用哪个版本，版本固化的依据 |
| `channel_bindings` | 从入站消息定位租户与 Agent |
| `sessions` | 会话定位与版本固化 |
| `session_events` | 会话事件，需验证 `sequence` 正确 |
| `inbound_events` | 入站幂等，ACK 前落库 |

### 能力配置为何拆表

Tool、扩展、MCP、Skill 四类能力配置从 `agent_versions` 拆为独立的绑定表，不合并为单列 JSON。原因是这四类均为不定长列表，随平台演进会持续增长，合并存储会导致该列不断膨胀，而每次装配 Runtime 都需整列读出并解析。

拆表的代价是装配时多出数次查询。这一代价由 Runtime 缓存吸收：Runtime 按 `tenant + version` 缓存，而已发布版本不可变，缓存不会失效，因此查询只发生在首次装配。

`prompt` 与 `model` 不拆表。二者是一个版本恰好一份的定长配置，拆出去只增加查询次数，因此直接作为 `agent_versions` 的列。

四张绑定表与 `agent_versions` 同为不可变数据：发布后不再修改，修改能力配置一律创建新版本。因此版本回滚时能力配置随之回滚，不会出现版本未变而权限已变的情况。

### 推迟到二期

| 表 | 推迟原因 |
|---|---|
| `tool_definitions` | 一期绑定表直接存 Tool 名，实现在代码中注册。定义表用于 Admin 页面渲染与反查影响面，二期需要 |
| `extension_definitions` | 同上 |
| `mcp_servers` | 一期不实际连接 MCP，绑定表可为空 |
| `knowledge_bases` 与绑定表 | 一期无知识库 |
| `channel_users` | 一期为 Mock 通道，`external_user_id` 可直接作为内部用户。映射规则在接入真实通道且存在第二个租户后才有意义 |
| `backend_configs` | 一期只有一个后端 |
| `backend_bindings` | 同上 |

推迟后端两张表不影响 Storage Router 的成立。路由的关键是接口形状与查找逻辑，而非配置来源：`StorageRouter` 按 `tenant + agent + data_type` 三元组查找的签名与内部逻辑在一期即定死，映射先从配置文件读取。二期改为读表时只动 Provider 内部，接口不变。同时省去解析连接引用与建立连接池的一整套逻辑。

## 2. 通用约定

- 物理主键统一为自增 `BIGINT UNSIGNED`，业务标识另立 `VARCHAR` 唯一键。业务标识用于跨进程传递与日志，不暴露自增值；
- 除 `tenants` 外所有表携带 `tenant_id`，索引以 `tenant_id` 起头；
- 枚举值使用 `VARCHAR` 而非 `ENUM`，便于增加取值而不改表结构；
- 不使用外键约束，关联关系由应用层保证；
- 关键表预留 JSON 扩展列；
- 字符集 `utf8mb4`，时间列统一 `DATETIME(3)`。

## 3. 与 Redis 的分工

MySQL 存长期数据：配置、会话元数据、会话事件、幂等记录。

Redis 存运行时状态：Session State、Session 租约、Session 信箱。这三类均需要 TTL 与原子操作，且只覆盖正在执行的会话，量级不大。

## 4. 表结构

### 4.1 tenants

```sql
CREATE TABLE tenants (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id  VARCHAR(64)  NOT NULL COMMENT '业务标识',
  name       VARCHAR(128) NOT NULL,
  status     VARCHAR(32)  NOT NULL DEFAULT 'active' COMMENT 'active / suspended',
  settings   JSON         NULL COMMENT '预留：预算、限流等租户级策略',
  created_at DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_tenant (tenant_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='租户';
```

### 4.2 agent_apps

```sql
CREATE TABLE agent_apps (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id    VARCHAR(64)  NOT NULL,
  agent_app_id VARCHAR(64)  NOT NULL,
  name         VARCHAR(128) NOT NULL,
  description  VARCHAR(512) NULL,
  status       VARCHAR(32)  NOT NULL DEFAULT 'active',
  created_at   DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at   DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_app (tenant_id, agent_app_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='Agent 应用';
```

### 4.3 agent_versions

已发布版本不可修改，配置变化时创建新版本。修改 Prompt、模型、Tool、扩展、MCP、Skill 均属配置变化，一律走新版本。

```sql
CREATE TABLE agent_versions (
  id                BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id         VARCHAR(64)  NOT NULL,
  agent_app_id      VARCHAR(64)  NOT NULL,
  version           VARCHAR(64)  NOT NULL COMMENT '如 v1、v2',
  status            VARCHAR(32)  NOT NULL DEFAULT 'draft' COMMENT 'draft / published / archived',
  system_prompt     TEXT         NULL,
  model_name        VARCHAR(128) NOT NULL,
  model_api_key_ref VARCHAR(255) NULL COMMENT '密钥引用，不存明文',
  model_params      JSON         NULL COMMENT 'temperature、max_tokens 等调用参数',
  description       VARCHAR(512) NULL,
  published_at      DATETIME(3)  NULL,
  created_by        VARCHAR(64)  NULL,
  created_at        DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at        DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_version (tenant_id, agent_app_id, version)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='Agent 版本配置';
```

Prompt 与模型配置作为列直接存放，因二者是一个版本恰好一份的定长配置。`model_params` 保留 JSON，因调用参数因模型而异且体积很小。

Tool、扩展、MCP、Skill 四类能力配置存于下列四张绑定表，理由见第 1 节。

### 4.4 agent_tool_bindings

```sql
CREATE TABLE agent_tool_bindings (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id    VARCHAR(64)  NOT NULL,
  agent_app_id VARCHAR(64)  NOT NULL,
  version      VARCHAR(64)  NOT NULL,
  tool_name    VARCHAR(128) NOT NULL,
  mode         VARCHAR(16)  NOT NULL DEFAULT 'allow' COMMENT 'allow / deny / ask',
  params       JSON         NULL COMMENT '该版本对此 Tool 的超时、限流等覆盖配置',
  created_at   DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_tool (tenant_id, agent_app_id, version, tool_name),
  KEY idx_tool_name (tool_name) COMMENT '反查哪些版本在使用某个 Tool'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='版本可用的 Tool';
```

`mode` 为 `ask` 表示该 Tool 调用前需二次确认。`idx_tool_name` 支持反查影响面，用于 Tool 下线或安全排查。

一期填入两个查询类 Tool，均为 `allow`。

### 4.5 agent_extension_bindings

```sql
CREATE TABLE agent_extension_bindings (
  id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id      VARCHAR(64)  NOT NULL,
  agent_app_id   VARCHAR(64)  NOT NULL,
  version        VARCHAR(64)  NOT NULL,
  kind           VARCHAR(16)  NOT NULL COMMENT 'plugin / guardrail / callback',
  extension_name VARCHAR(128) NOT NULL,
  enabled        TINYINT(1)   NOT NULL DEFAULT 1,
  priority       INT          NOT NULL DEFAULT 0 COMMENT '同类扩展的挂载顺序，值小者先执行',
  params         JSON         NULL,
  created_at     DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_ext (tenant_id, agent_app_id, version, kind, extension_name),
  KEY idx_ext_name (kind, extension_name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='版本启用的 Plugin、Guardrail、Callback';
```

`kind` 决定挂载到框架的哪一类扩展位，`extension_name` 对应代码中注册的实现名。表中只记录启用项与参数，实现不入表，因此新增一种扩展只需注册实现，不改表结构也不改装配逻辑。

`priority` 用于确定同类扩展的执行顺序。多个 Guardrail 的先后次序会影响结果，例如脱敏应在审计记录之前，因此顺序需可配置而非依赖插入顺序。

一期填入一个日志类 Callback，但装配需按列表遍历挂载，不可写死。

### 4.6 agent_mcp_bindings

```sql
CREATE TABLE agent_mcp_bindings (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id    VARCHAR(64)  NOT NULL,
  agent_app_id VARCHAR(64)  NOT NULL,
  version      VARCHAR(64)  NOT NULL,
  server_name  VARCHAR(128) NOT NULL COMMENT '二期起关联 mcp_servers',
  enabled      TINYINT(1)   NOT NULL DEFAULT 1,
  tool_filter  JSON         NULL COMMENT '仅暴露该 MCP 的部分 Tool 时使用',
  created_at   DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_mcp (tenant_id, agent_app_id, version, server_name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='版本使用的 MCP 服务';
```

一期不实际建立 MCP 连接，本表可为空。建表的目的是装配逻辑按四类能力统一遍历，二期接入 MCP 时不改装配结构。

`tool_filter` 存在的原因是一个 MCP 服务通常暴露多个 Tool，而租户可能只希望开放其中部分。

### 4.7 agent_skill_bindings

```sql
CREATE TABLE agent_skill_bindings (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id    VARCHAR(64)  NOT NULL,
  agent_app_id VARCHAR(64)  NOT NULL,
  version      VARCHAR(64)  NOT NULL,
  skill_name   VARCHAR(128) NOT NULL COMMENT '二期起关联 skills',
  enabled      TINYINT(1)   NOT NULL DEFAULT 1,
  params       JSON         NULL,
  created_at   DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_skill (tenant_id, agent_app_id, version, skill_name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='版本挂载的 Skill';
```

一期同样可为空，理由与 MCP 绑定表相同。

### 4.8 agent_deployments

```sql
CREATE TABLE agent_deployments (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id    VARCHAR(64) NOT NULL,
  agent_app_id VARCHAR(64) NOT NULL,
  env          VARCHAR(32) NOT NULL DEFAULT 'prod',
  routes       JSON        NOT NULL COMMENT '[{"version":"v1","weight":90},{"version":"v2","weight":10}]',
  strategy     JSON        NULL COMMENT '预留：按租户、通道、用户或标签灰度',
  updated_by   VARCHAR(64) NULL,
  created_at   DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at   DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_deploy (tenant_id, agent_app_id, env)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='环境发布与灰度权重';
```

一行代表一个环境，各版本权重存于 `routes`。调整权重与回滚均为单行更新，天然原子，不会出现权重之和不为 100 的中间态。若改为一行一个版本，调权重需要事务且存在中间态。

一期只写入一条权重 100 的记录，但 Gateway 侧按权重选版本的逻辑需真实实现。

### 4.9 channel_bindings

```sql
CREATE TABLE channel_bindings (
  id                 BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  channel_binding_id VARCHAR(64)  NOT NULL,
  tenant_id          VARCHAR(64)  NOT NULL,
  agent_app_id       VARCHAR(64)  NOT NULL,
  env                VARCHAR(32)  NOT NULL DEFAULT 'prod',
  channel            VARCHAR(32)  NOT NULL COMMENT 'mock / wecom / wechat_kf / telegram',
  external_app_id    VARCHAR(128) NULL COMMENT '通道侧应用标识',
  webhook_path       VARCHAR(255) NULL,
  secret_ref         VARCHAR(255) NULL COMMENT '密钥引用，不存明文',
  capabilities       JSON         NULL COMMENT '能力描述符，结构见第 6 节',
  status             VARCHAR(32)  NOT NULL DEFAULT 'active',
  created_at         DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at         DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_binding (channel_binding_id),
  UNIQUE KEY uk_webhook (webhook_path),
  KEY idx_tenant_app (tenant_id, agent_app_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='IM 账号与租户、Agent 绑定';
```

`webhook_path` 唯一，Gateway 据请求路径反查绑定，从而确定租户与 Agent。

### 4.10 sessions

```sql
CREATE TABLE sessions (
  id                 BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  session_id         VARCHAR(64)  NOT NULL,
  tenant_id          VARCHAR(64)  NOT NULL,
  agent_app_id       VARCHAR(64)  NOT NULL,
  agent_version      VARCHAR(64)  NOT NULL COMMENT '创建时固化，此后不随发布变化',
  channel            VARCHAR(32)  NOT NULL,
  channel_binding_id VARCHAR(64)  NOT NULL,
  scope              VARCHAR(16)  NOT NULL COMMENT 'single / group',
  scope_key          VARCHAR(128) NOT NULL COMMENT '单聊为 external_user_id，群聊为 external_group_id',
  internal_user_id   VARCHAR(64)  NULL COMMENT '群聊为空',
  last_sequence      BIGINT UNSIGNED NOT NULL DEFAULT 0,
  status             VARCHAR(32)  NOT NULL DEFAULT 'active',
  last_active_at     DATETIME(3)  NULL,
  created_at         DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at         DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_session (session_id),
  UNIQUE KEY uk_scope (channel_binding_id, scope, scope_key),
  KEY idx_tenant_active (tenant_id, last_active_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='会话元数据';
```

`uk_scope` 直接对应会话定位规则：单聊由 `channel_binding_id + external_user_id` 定位，群聊由 `channel_binding_id + external_group_id` 定位，两者统一到 `scope` 与 `scope_key` 两列。

`agent_version` 在创建会话时按 Deployment 权重选定并写入，此后该会话固定使用该版本，因此调整权重或回滚不影响进行中的会话。

### 4.11 session_events

```sql
CREATE TABLE session_events (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id     VARCHAR(64) NOT NULL,
  session_id    VARCHAR(64) NOT NULL,
  sequence      BIGINT UNSIGNED NOT NULL COMMENT '会话内单调递增',
  event_type    VARCHAR(32) NOT NULL COMMENT 'user_message / agent_message / tool_call / tool_result / system',
  role          VARCHAR(16) NULL,
  content       JSON        NULL,
  request_id    VARCHAR(64) NOT NULL,
  trace_id      VARCHAR(64) NULL,
  agent_version VARCHAR(64) NULL,
  created_at    DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_seq (session_id, sequence),
  KEY idx_request (request_id),
  KEY idx_tenant_time (tenant_id, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='会话事件';
```

`uk_seq` 是顺序正确性的硬保证：同一会话的相同 `sequence` 无法写入两次，重复执行或并发写入会在数据库层直接失败，而非产生错乱数据。

### 4.12 inbound_events

入站幂等记录。写入顺序为先落库、再回 ACK、最后入队，因此本表也是在途请求的唯一可靠记录。

```sql
CREATE TABLE inbound_events (
  id                 BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id          VARCHAR(64)  NOT NULL,
  channel_binding_id VARCHAR(64)  NOT NULL,
  external_event_id  VARCHAR(128) NOT NULL COMMENT '通道侧事件或消息标识',
  request_id         VARCHAR(64)  NOT NULL,
  trace_id           VARCHAR(64)  NULL,
  session_id         VARCHAR(64)  NULL COMMENT '识别会话后回填',
  payload            JSON         NULL COMMENT '标准化后的统一消息，供重放使用',
  state              VARCHAR(32)  NOT NULL COMMENT 'processing / succeeded / delivery_failed / failed',
  attempts           INT          NOT NULL DEFAULT 0,
  last_error         VARCHAR(512) NULL,
  created_at         DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at         DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_event (channel_binding_id, external_event_id),
  KEY idx_state (state, updated_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='入站幂等记录';
```

`uk_event` 拦截通道的重复投递。`state` 区分执行与投递两个阶段，其中 `delivery_failed` 表示 Agent 已执行完成但回复未送达，该状态只重试投递，不重新执行 Agent 与 Tool。`idx_state` 用于扫描长时间停留在 `processing` 的记录，供对账与重放。

## 5. Runtime 装配的读取顺序

装配 Runtime 需读取版本配置与四张绑定表。这一组读取即 `RuntimeProvider` 的输入，顺序在一期定死。

```text
按 tenant + agent_app + version 读 agent_versions   得到 Prompt 与模型配置
按同一组键读 agent_tool_bindings                    得到 Tool 列表与 allow / deny / ask
按同一组键读 agent_extension_bindings               得到扩展列表，按 kind 分组并依 priority 排序
按同一组键读 agent_mcp_bindings                     一期为空
按同一组键读 agent_skill_bindings                   一期为空
```

五次读取的键完全一致，可合并为一次查询后在内存中分组。是否合并属实现细节，但装配的输入结构不变。

装配结果按 `tenant + version` 缓存。已发布版本不可变，缓存不会失效，因此上述读取只发生在首次装配，拆表带来的查询开销不落在请求主路径上。

扩展列表需按列表遍历挂载，不可写死。一期该列表只有一个日志类 Callback，二期往列表中追加即可，装配签名不变。

## 6. capabilities 结构

通道能力描述符，Gateway 与 Worker 据此决定行为，而非所有通道走同一路径。

```json
{
  "inbound_mode": "payload",
  "supports_push": true,
  "supports_edit": false,
  "max_text_length": 2048,
  "rate_limit_per_min": 20
}
```

| 字段 | 含义 |
|---|---|
| `inbound_mode` | `payload` 表示回调自带消息内容，`fetch` 表示回调仅通知、需再拉取 |
| `supports_push` | 是否支持主动推送。ACK 后异步回复依赖此能力 |
| `supports_edit` | 是否支持编辑已发送消息 |
| `max_text_length` | 单条消息长度上限，超出需拆分 |
| `rate_limit_per_min` | 每分钟发送条数限制 |

一期 Mock 通道同样填写该列，保证二期接入真实通道时结构不变。

## 7. 初始数据

一期预置以下数据，构成一条可运行的链路：

```text
tenants                   tenant-demo
agent_apps                tenant-demo / assistant
agent_versions            tenant-demo / assistant / v1，status=published
agent_tool_bindings       v1 → search、calculator，均为 allow
agent_extension_bindings  v1 → callback / request_logger
agent_deployments         tenant-demo / assistant / prod，routes=[{v1,100}]
channel_bindings          cb-demo，channel=mock，webhook_path=/webhook/mock/demo
```

`agent_mcp_bindings` 与 `agent_skill_bindings` 建表但不写入数据。

`sessions`、`session_events`、`inbound_events` 由运行时写入，不预置数据。
