## 拆分原则

设计文档按五个模块横向组织，实现按链路纵向切分。每一期结束都必须是能跑通的完整链路，不留半成品模块。

分期依据：**后期难改的进一期，后期只是"加更多同类"的往后放**。

- 一期确定拓扑与接口边界，每种组件只做一个实例，但每一层都是真实的；
- 二期在同一骨架上铺开广度，不动结构；
- 三期补治理、可观测与交付物。

## 技术栈与代码组织

技术栈：tRPC-Agent-Go + Gin + MySQL + Redis，不引入 tRPC-Go RPC 框架。

代码组织为一个仓库编译出 `cmd/gateway` 与 `cmd/worker` 两个可执行文件，包划分与系统架构图分层对应。详见 `docs/技术实现文档/代码组织方案.md`，本文不重复。

流式响应不在交付范围内，仅保留输出函数这一处扩展点。

## 一期（8/28 – 8/31）架构骨架

一次性把真实拓扑搭起来，内容单薄但不简化结构。

- Gateway 与 Worker 拆为两个进程，中间通过消息队列异步分发；同一 Session 的顺序由 Session 租约保证，不依赖队列的顺序消息特性；
- 配置从配置库读取，不硬编码：`tenants`、`agent_apps`、`agent_versions`、`agent_deployments` 建表，先只写入一条数据；
- Runtime 按 `tenant_id + agent_version` 动态装配，不写死单个 Agent；
- 租户上下文（`tenant_id`、`agent_app_id`、`session_id`、`request_id`、`trace_id` 等）全链路贯穿；
- Storage 按 `tenant_id + agent_app_id + data_type` 真实路由，只注册一个后端但走完整路由逻辑；
- 入站处理顺序固定为：幂等记录落库 → ACK → 入队；
- 通道只实现 MockChannel（HTTP 收发），但 `Channel` 接口与能力描述符按真实通道的形状定义。

核心接口在本期定死，后续两期只填实现、不改结构：`Channel`、`SessionDispatcher`、`StorageRouter`、`RuntimeProvider`。

**出口标准**：两个进程 + 消息队列 + Redis + SQL 起来后，发一条消息经过完整链路返回，Session 与 Event 正确落库。

## 二期（9/1 – 9/5）平台化铺开

在一期骨架上增加广度，本期分量最重，需预留余量。

- 接入一个真实 IM 通道（优先企业微信），落地入站即刻 ACK + 主动推送回复；
- 扩展到多租户多 Agent，验证配置隔离与数据隔离；
- Admin API 提供租户与 Agent 配置的增删改查；
- Worker 支持多副本运行；
- Runtime 缓存增加容量上限；
- Storage 注册多个后端，验证按租户路由；
- 补充死信处理，避免单条毒消息阻塞 Session 信箱。
